## 1. はじめに

Nextorは、MSXコンピュータ用のディスクオペレーティングシステムであるMSX-DOS 2の拡張版です。MSX-DOS 2.31をベースにしており、同バージョンとの高い互換性を備えています。

本書は、Nextor用のストレージデバイスドライバを開発するプログラマー向けのガイドです。本書を読み進める前に、*『Nextor 2.1 ユーザーズマニュアル』*を読んでNextorの基本機能に慣れておくことをお勧めします。また、必須ではありませんが、NextorがMSX-DOS 2に新しく追加した機能（ドライバ開発以外の観点）のリファレンスである*『Nextor 2.1 プログラマーズリファレンス』*にも目を通しておくことをお勧めします。

## 2. Nextorカーネルのアーキテクチャ

本セクションでは、従来のMSX-DOSカーネルの動作方法とNextorでの変更点を交えながら、Nextorカーネルのアーキテクチャに関する基本概念を説明します。ここに記載されている情報は、ドライバ開発者がドライバコードの実行環境（コンテキスト）を理解するのに役立ちます。

### 2.1. MSX-DOS 1カーネル

初代MSX-DOSカーネル（バージョン1）は、最初は外部のMSXフロッピーディスクコントローラに搭載されたROMとして、後にはフロッピーディスクドライブを内蔵したMSXコンピュータの内蔵ROMとして提供されていました。これは、割り当てられたスロットのページ1アドレス空間（4000hから7FFFh）を使用する16KのROMです。

MSX-DOS 1カーネルは、主に以下の2つの部分に分かれています。

* **カーネル共通コード**: ファンクションコールやFATファイルシステム管理コードなど、ハードウェアに依存しないコードが含まれています。ROM内のほとんどのコードがこの部分にあたります。

* **ディスクドライバ**: カーネルコードからの要求に応じて、主にディスクセクタの読み書きを行うために、ストレージデバイスに物理的にアクセスするコードです。標準化された入出力パラメータを持つ一連のルーチンで構成されています。

カーネル共通コードは、100%ドライバから独立しているわけではありません。使用するディスクドライバに応じてパッチを当てる必要がある箇所がいくつか存在します。1つはドライバによって制御されるドライブユニットの数を指定する部分、もう1つはドライバが必要とするページ3ワークエリアのサイズを指定する部分です。

図1に、MSX-DOS 1カーネルの構造を示します。

```
4000h +---------------------+
      |                     |
      |                     |
      |                     |
      |        カーネル     |
      |       共通コード    |
      |                     |
      |                     |
      +---------------------+
      |                     |
      |   ディスクドライバ  |
      |                     |
7FFFh +---------------------+
```

*図1 - MSX-DOS 1カーネルの構造*

MSXコンピュータには、最大4つのMSX-DOSカーネルROMを同時にアクティブにできます。複数存在する場合、最も小さいスロット番号のROMが「マスター」（カーネル共通コードが実際に実行されるもの）になり、それ以外は「スレーブ」（ドライバコードのみが実行されるもの）になります。

MSX-DOSはストレージデバイスをドライブ文字（A:やB:など）として認識し、ディスクドライバは1つ以上のドライバユニットを提供します。これらのマッピングは一対一で固定されており、たとえばドライブA:は最初のカーネルのドライバユニット0に、ドライブB:はドライバユニット1に、といった形でマッピングされます。

### 2.2. MSX-DOS 2カーネル

MSX-DOS 2カーネルは、最初はストレージハードウェアを伴わないカートリッジとして登場し、MSX-DOS 1カーネルが搭載された既存のストレージコントローラと併用することを想定していました。その後、MSX turboRコンピュータに内蔵されました。

MSX-DOS 2カーネルは、MSX-DOS 1カーネルと同様にスロットのページ1アドレス空間を使用しますが、サイズは64Kあります。この空間は4つの16Kバンクに分割されており、バンク切り替え機構を使用して一度に1つのバンクのみが可視になるよう制御されます。各バンクの内容は以下の通りです。

* **バンク0**: カーネル共通コードと、ディスクドライバコード。

* **バンク1および2**: カーネル共通コード。

* **バンク3**: MSX-DOS 1カーネルのコピーと、ディスクドライバコードのコピー（MSX turboRマシンのみ）。

図2に、MSX-DOS 2カーネルの構造を示します。

```
               バンク 0           バンク 1 および 2          バンク 3
4000h +---------------------+---------------------+---------------------+
      |     ページ0コード   |     ページ0コード   |                     |
40FFh +---------------------+---------------------+                     |
      |    0 (バンクID)     |   1/2 (バンクID)    |                     |
4100h +---------------------+---------------------+                     |
      |                     |                     |                     |
      |       バンク 0      |      バンク 1/2     |       バンク 3      |
      |   カーネルコード    |   カーネルコード    |   カーネルコード    |
      |                     |                     | (MSX-DOS 1カーネル) |
      |                     |                     |                     |
      +---------------------+                     |---------------------+
      |                     |                     |                     |
      |   ディスクドライバ  |                     |   ディスクドライバ  |
      |                     |                     |                     |
7FD0h +---------------------+---------------------+---------------------+
      |バンク切り替えコード |バンク切り替えコード |バンク切り替えコード |
7FFFh +---------------------+---------------------+---------------------+
```

*図2 - MSX-DOS 2カーネルの構造*

すべてのバンクに共通する部分が3つあります（バンク3にはバンク切り替えコードのみが含まれます）。

* **ページ0コード**: 255バイトの長さで、タイマー割り込みルーチンのエントリポイント、別バンクのコードを呼び出すためのルーチン、およびその他の便利なユーティリティコードが含まれています。

* **バンクID**: バンク番号を示す1バイトで、バンク間呼び出し（インターバンク呼び出し）を行うために必要です。

* **バンク切り替えコード**: 表示されるバンクを変更するために必要です。ここに配置される具体的なコードは、使用されるROMマッパーのタイプに依存します（元のDOS 2カートリッジのマッピングはASCII16です）。

DOS 2モードで起動すると、バンク0が永続的に切り替えられ、他のバンクはバンク0のコードがそれらのバンク上のルーチンを呼び出すかデータにアクセスする必要があるときにのみ、一時的に切り替えられます。DOS 1モードで起動すると、起動時にバンク3が切り替えられ、そのまま永続的に保持されます。

MSX-DOS 1カーネルの場合と同様に、最大4つのMSX-DOSカーネルROMを同時にアクティブにでき、そのうちの1つが「マスター」となり、他が「スレーブ」となります。ただし、マスターの決定方法が異なり、最小のスロット番号のカーネルが選ばれるのではなく、最もバージョン番号の高いカーネルがマスターになります（同じバージョン番号のカーネルが複数ある場合は、最も小さいスロット番号のカーネルがマスターに選ばれます）。

### 2.3. Nextorカーネル

Nextorカーネルは、MSX-DOS 2カーネルに基づいたアーキテクチャを採用していますが、いくつかの重要な変更が加えられています。

* **バンク数の増加**: 現行バージョンでは、パーティション管理コード用に1つの追加バンク、および内蔵パーティションツールのために2つの追加バンクが存在します。

* **デバイスドライバの独立**: ディスクドライバ（Nextorの用語では「デバイスドライバ」）コードは、カーネルのバンク0およびバンク3の末尾に埋め込まれなくなりました。代わりに、ドライバ専用のバンクが1つ用意され、これはカーネル共通コードの最後のバンクの直後に配置されます。必要に応じて、ドライバは複数のバンクにまたがることができます。

* **ドライバ構造の刷新**: デバイスドライバの構造が完全に新しくなりました。ストレージデバイスにアクセスするルーチンはもちろんのこと、BASICの拡張コマンド（「CALL」コマンド）、拡張BIOSコマンド、タイマー割り込みサービスルーチンを簡単に追加できる拡張ポイント（フック）が用意されています。

* **ページ0コードの拡張**: ページ0コードが変更され、追加のユーティリティルーチンが含まれるようになりました。これらのルーチンはドライバコードから便利に呼び出すことができます。

* **カーネルサイズ情報の追加**: すべてのバンクのアドレス4FFEhに新しい情報バイトが追加されました。これには、16Kバンク単位でのカーネル共通コードのサイズ（数）が含まれています（この値は、ドライバが配置されている最初のバンク番号と見なすこともできます）。

* **MSX-DOS 1互換モードの強化**: バンク3のMSX-DOS 1カーネルが変更され（ページ0コードやバンクIDの追加など）、MSX-DOS 1モードからでもデバイスドライバへの呼び出しを実行できるようになりました。

* **フリースペースの提供**: バンク0および3に1Kの未使用スペースがあります（アドレス7BD0hから7FCFhに表示されます）。このスペースにはカーネルコードは含まれておらず、ドライバに必要な共通コードやデータを配置するために使用できます。詳細については、「[4.7.1. カーネルメインバンクの空きスペース](#471-カーネルメインバンクの空きスペース)」を参照してください。

* **ダイレクトエントリーポイント**: カーネルのバンク0および3に5つのエントリポイント（アドレス7850hから開始）があり、これらはドライババンク内の対応する5つのエントリポイントへリダイレクトされます。これにより、ドライバはカーネルスロットへの直接のインタースロット呼び出しを介してアクセス可能なコードを提供できます。詳細については、「[4.4.7. DRV_DIRECT0/1/2/3/4 (4142h, 4145h, 4148h, 414Bh, 414Eh)](#447-drv_direct01234-4142h-4145h-4148h-414bh-414eh)」を参照してください。

図3に、Nextorカーネルの構造を示します。

```
           バンク 0〜(K-1)            バンク K        バンク (K+1)〜... (オプション)
4000h +---------------------+---------------------+---------------------+
      |     ページ0コード   |     ページ0コード   |     ページ0コード   |
      +---------------------+---------------------+---------------------+
40FEh |          K          |          K          |          K          |
      +---------------------+---------------------+---------------------+
40FFh |      バンクID       |     K (バンクID)    |      バンクID       |
4100h +---------------------+---------------------+---------------------+
      |                     |                     |                     |
      |        バンク       |                     |        追加の       |
      |   カーネルコード    |    ドライバコード   |    ドライバコード   |
      |                     |                     |                     |
      |                     |                     |                     |
      |                     |                     |                     |
7BD0h +---------------------+                     |                     |
      | 使用可能な1Kスペース |                     |                     |
      |  (バンク0および3)   |                     |                     |
7FD0h +---------------------+---------------------+---------------------+
      |バンク切り替えコード |バンク切り替えコード |バンク切り替えコード |
7FFFh +---------------------+---------------------+---------------------+
```

*図3 - Nextorカーネルの構造（「K」はカーネル共通コードのバンク数）*

Nextorは、システム内に複数のカーネルが見つかった場合にどのカーネルをマスターにするかを決定するために、MSX-DOS 2と同じルールを使用します（最もバージョン番号の高いカーネルが選ばれます）。ただし、これは他のNextorカーネル同士にのみ適用されます。Nextorは、システム内に存在する他のMSX-DOS 1または2のカーネルを、そのバージョン番号に関係なく常にオーバーライド（優先）します。

## 3. 組み込みドライバを含むNextorカーネルの作成

MSXコンピュータで使用可能な完全なNextorカーネルROMを作成するには、最大4つのコンポーネントが必要です。

* **Nextorカーネルベースファイル**: カーネル共通コード、すなわち図3に示す「バンク0〜(K-1)」の部分を含むファイル（NEXTOR.BASE.DAT）です。そのバンク切り替えコードはASCII16マッパー（MSX-DOS 2カーネルで使用されていた元のマッパー）用になっています。

* **デバイスドライバファイル**: セクション4で説明する規則と構造に従って作成する必要があります。そのサイズは正確に16080バイト（16Kからページ0コードのサイズとバンク切り替えコードのサイズを引いたもの）でなければなりません。ドライバが複数のバンクにまたがる場合、この条件は各バンクに適用されます。

* **バンク切り替えコードファイル**（ターゲットハードウェアで使用されるマッパーがASCII16ではない場合のみ）：このコードは、完成したカーネルを書き込むROMカートリッジがサポートしているマッピングタイプに依存します。ASCII8およびASCII16マッパー用のコンパイル済みバンク切り替えコードファイルが提供されています。その他のマッパータイプについては、「[3.3. バンク切り替えコードの規則](#33-バンク切り替えコードの規則)」に従ってカスタムコードファイルを作成する必要があります。

  *注意*: 16Kバンクではなく8Kバンクで動作するROMマッパーは、LD (xxxxh),A 命令を使用してメモリマップドポートに1バイトを書き込むことで、ページ1の前半（4000h〜5FFFh）に見えるバンクを選択できる場合にのみサポートされます。これはたとえばASCII8の場合にあたります。

* **オプションの追加データ**: オプションで、バンク0および3の1Kの未使用スペースに配置されるコード（詳細は「[4.7.1. カーネルメインバンクの空きスペース](#471-カーネルメインバンクの空きスペース)」を参照）。

完全なNextorカーネルROMファイルを作成する手順は、基本的にカーネルベースファイルにドライバコードを追加し、その結果ファイルに適切なバンク切り替えコードをパッチすることです。これは手動で行うことも、MKNEXROMユーティリティを使用して行うこともできます。両方のオプションを以下に説明します。

### 3.1. 手動での作成

手動で完全なNextor ROMファイルを作成する場合、以下の手順に従います。記載されているファイル位置はゼロベース（0から始まるオフセット）です。

1. カーネルベースファイル（NEXTOR.BASE.DAT）のコピーを作成します。
2. そのコピーの末尾に「ページ0コード」を追加します。このコードは、カーネルベースファイルの最初の255バイトからそのままコピーできます。
3. その末尾に、値 `K`（カーネルベースファイルのバンク数、ドライバのバンクIDとなります）を1バイト追加します。値 `K` は、カーネルベースファイルの254バイト目の位置から読み取ることができます。
4. その末尾に「ドライバファイル」を追加します（ドライバファイルは正確に16080バイトの長さでなければならず、足りない場合はパディングが必要です）。
5. その末尾に「バンク切り替えコード」を追加します。ASCII16マッパーをサポートするハードウェア向けのファイルを作成する場合は、このコードをカーネルベースファイルの最後の48バイトからそのままコピーできます。それ以外の場合は、カスタムマッピングコードを用意する必要があります。
6. ドライバコードが1つのバンクに収まらない場合は、必要に応じてバンクIDをインクリメントしながら、手順2〜5を繰り返して追加のバンクを結合します。
7. 必要に応じて、バンク0および3の1Kのフリースペースにカスタムコードやデータをパッチします。用意したデータ（最大1K長）を、ファイルの `3BD0h` と `FBD0h` の2カ所に書き込みます。
8. ターゲットハードウェアのマッパータイプがASCII16ではない場合、カーネル共通コードバンク（手順3で取得した `K` 個の16Kブロックの最後にある各48バイト）のバンク切り替えコードを、カスタムバンク切り替えコードで上書きパッチします。
9. ターゲットハードウェアのマッパータイプがASCII16ではない場合、手順5と8で使用したのと同じカスタムバンク切り替えコードを、ファイルのオフセット `2012` にも配置します。
10. **ROMマッパーが8Kバンクを使用する場合のみ**、以下の処理を行います。
    * 生成されたファイルのオフセット `F7h` に、`LD (xxxxh),A` 命令を書き込みます。ここで `xxxx` は、ページ1の前半（4000h-5FFFh）に表示される8Kバンクを選択するメモリマップドポートのアドレスです。これは、`32h` バイトに続いて `xxxxh` をリトルエンディアン形式で記述したものです。
    * 上記のステップを、ファイルのすべての16Kバンクに対して繰り返します。つまり、`(4000h * n) + F7h` の位置に `LD (xxxxh),A` 命令を書き込みます。ここで `n` は、0から（ROMファイル全体の16Kバンク数 - 1）まで変化します。

この手順により、デバイスドライバが適切に埋め込まれた、すぐに使用できる完全なNextor ROMファイルが作成されます。生成されたROMファイルをさらにパッチしたり変更したりする必要はありません。

### 3.2. 使用するMKNEXROMユーティリティ

手動ですべての手順を実行する代わりに、通常は提供されているMKNEXROMユーティリティを使用するのが便利です。このツールを使用すると、新しいNextorカーネルROMファイルを作成できるだけでなく、マッパーコードを変更したり、バンク0および3の空き1Kエリアにコンテンツを追加したりして、既存のファイルを変更することもできます。

MKNEXROMはWindows用のコマンドライン実行ファイルとして提供されていますが、標準C言語のソースコードも提供されているため、他のプラットフォームへの移植も容易です。

MKNEXROMツールの構文は以下の通りです。

```
MKNEXROM <basefile> <newfile> [/d:<driverfile>] [/m:<mapperfile>]
         [/e:<extrafile>] [/8:<8K bank selection port address>]
```

`<basefile>` には以下のいずれかを指定できます。

* Nextorカーネルベースファイル（カーネル共通コードのみを含むファイル）。
* すでにドライババンクが追加されている完成済みのNextorカーネルROMファイル。

`<driverfile>` は、ドライバコードを含むファイルです。セクション4で説明する規則と構造に準拠した有効なドライバでなければなりません。このファイルの構成は以下の通りである必要があります。

1. 256バイトのダミースペース。
2. ドライバ署名。
3. ドライバジャンプテーブル。
4. ドライバコード本体。

ドライバが複数の16Kバンクにまたがる場合は、各追加16Kブロックの先頭に以下を配置します。

5. 256バイトのダミースペース。
6. 追加のドライバコードまたはデータ。
7. 16Kの境界に合わせるためのダミースペース（最後のバンクでは不要です）。

`<basefile>` にドライバ無しのカーネルベースファイルを指定した場合は、ドライバファイルの指定が必須となります。すでに完成しているカーネルROMファイルを指定した場合は、ドライバファイルの指定は禁止されます。

`<mapperfile>` は、バンク切り替えコードを含むファイルです。マッパーファイルが指定されない場合、ベースファイル自体からマッパーコードが抽出され、ドライバコードの末尾に追加されます。

`<extrafile>` は、生成されるROMファイルに埋め込む追加コードまたはデータを含むファイルです。この追加データは最大1Kバイトで、バンク0および3のアドレス `7BD0h` に配置されます。これにより、アプリケーションからカーネルスロットへの標準的なインタースロット呼び出し（RDSLTやCALSLTなど）を介して、アドレス `7BD0h` でこのコードやデータにアクセスできるようになります。詳細については、「[4.7.1. カーネルメインバンクの空きスペース](#471-カーネルメインバンクの空きスペース)」を参照してください。

`/8` は、ROMマッパーが8Kバンクを使用する場合にのみ使用します。`<8K bank selection port address>` には、ページ1の前半（4000h〜5FFFh）に見える8Kバンクを選択するメモリマップドポートのアドレスを指定します（ASCII8マッパーの場合は `6000h` など）。これにより、生成されたROMのブートコードが適切にパッチされ、このタイプのマッパーがサポートされます。

8Kバンクを使用するROMマッパーで `/8` パラメータを使用する代わりに、マッパーファイルの先頭にヘッダーを追加してMKNEXROMに自動パッチを行わせることもできます。このヘッダーは、`FFh` バイトに続いて、バンク選択ポートアドレスをリトルエンディアン形式で記述したものです。詳細は以下を参照してください。

### 3.3. バンク切り替えコードの規則

生成されたROMを書き込むターゲットハードウェアのマッパータイプがASCII16以外の場合、コンパイル済みのカスタムマッピングコードを含むファイルを提供する必要があります。このコードは以下の規則に従う必要があります。

1. 最大48バイトの長さであること。
2. レジスタ A で渡された番号（0から開始）の16K ROMバンクを、ページ1（4000h〜7FFFh）に切り替えること。ROMスロットはすでにページ1に切り替えられていると仮定されます。
3. レジスタ AF のみを破壊してよいこと。その他のレジスタはすべて保持されなければなりません。
4. 任意のアドレスで実行できるように作成されていること（絶対ジャンプや自己参照アドレスを含めることはできません）。

参考として、以下はASCII8マッパー用の有効なバンク切り替えコードのソースコードです。

```
rlca
ld (6000h),a
inc a
ld (6800h),a
ret
```

上記のコードをコンパイルしたファイルをマッパーファイルとしてMKNEXROMに渡す場合、コマンドラインに `/8:6000` パラメータを追加して、生成されるROMファイルに8Kバンク用マッパーの適切なパッチを適用させる必要があります。同じファイルを、ヘッダーを付与して `/8` パラメータを不要にする形式に書き直すと、以下のようになります。

```
db 0FFh
dw 6000h
rlca
ld (6000h),a
inc a
ld (6800h),a
ret
```

## 4. Nextorドライバの構造

本セクションでは、Nextor用デバイスドライバの開発に必要な詳細を説明します。必要な要素、その配置場所、要求されるルーチンの入出力パラメータについて解説します。

なお、デバイスを一切管理しない有効なダミードライバのソースコード（[DRIVER.ASM](DRIVER.ASM)）もあわせて提供されています。このファイルを、独自のドライバを開発するためのスケルトン（骨組み）として使用できます。

### 4.1. ドライブベースドライバとデバイスベースドライバ

Nextorのデバイスドライバを開発する際、開発者は **ドライブベース（drive-based）** と **デバイスベース（device-based）** の2つのドライバスタイルから選択する必要があります。

* **ドライブベースドライバ**は、MSX-DOSのディスクドライバと同様の性質を持ちます。これらは一連の「ドライブユニット」を公開し、Nextorは各ユニットに固定のドライブ文字を割り当てます。必要なドライブからデバイス、あるいはパーティションへのマッピングは、ドライバ自身が行う必要があります。これらのドライバが公開するストレージデバイスアクセス用のルーチンセットは、MSX-DOSドライバで使用されていたものと同じです（DSKIO, DSKCHG, GETDPB, CHOICE, DSKFMT, MTOFF）。

* **デバイスベースドライバ**は、完全に異なるアプローチを使用します。これらはドライバユニットではなく、直接「ストレージデバイス」を公開します。また、デバイスへの生アクセス（raw access）用のルーチンを公開し、ドライブからデバイスやパーティションへのマッピングはNextorカーネル自体が管理します。

一般的には、**デバイスベースドライバ**の開発をお勧めします。実装すべきルーチンがより単純になり、ドライバコードはパーティションを意識することなく、絶対デバイスセクタを読み書きするだけで済むからです。また、Nextorの内蔵デバイスパーティションツールは、デバイスベースドライバによって制御されるデバイスにのみパーティションを作成できます。ただし、既存のMSX-DOS用ドライバをNextorに簡単に移植したい場合には、ドライブベーススタイルを選択するのも良い方法です。

Nextorは、起動時にデバイスベースドライバに割り当てられたドライブに対して自動的なドライブ-デバイス・パーティションマッピングを実行します。このマッピングは、後でMAPDRVユーティリティを使用して変更できます（ただし、ドライバは [DRV_CONFIG](#448-drv_config-4151h) を実装することで、この自動割り当ての一部をカスタマイズまたはバイパスできます）。詳細は『Nextor 2.1 ユーザーズマニュアル』を参照してください。

### 4.2. ページ0のルーチンとデータ

本セクションでは、ドライババンクを含むすべてのNextorバンクのページ0（アドレス4000h〜40FFh）で利用可能なユーティリティルーチンとデータについて説明します。これらのルーチンは、ドライバコードにおける便利なヘルパーとして機能します。

「3. 組み込みドライバを含むNextorカーネルの作成」で説明したように、完成したNextorカーネルROMが生成されると、ページ0のコードはすべてのドライババンクの先頭にコピーされて埋め込まれます。

#### 4.2.1. GSLOT1 (402Dh)

現在ページ1に切り替えられているスロット（つまり、現在のドライバコードが実行されているスロット）の値をレジスタ A に取得します。F 以外のすべてのレジスタが保存されます。

*注意*: このルーチンは直接呼び出すことはできません。以下のように、バンク0へのインターバンク呼び出しを介して呼び出す必要があります。

```
XOR A
LD IX,GSLOT1
CALL CALBNK
```

#### 4.2.2. RDBANK (403Ch)

指定した別のバンクから1バイトを読み取ります。読み取り対象のバンクへのインターバンク呼び出しとして実行し、読み取り先アドレスを HL に設定して呼び出す必要があります。

```
LD A,<バンク番号>
LD HL,<バイトアドレス> (ページ1のアドレスである必要があります)
LD IX,RDBANK
CALL CALBNK
```

読み取ったバイトは A に返されます。F 以外のすべてのレジスタが保存されます。

#### 4.2.3. CALLB0 (403Fh)

一時的にカーネルメインバンク（通常はバンク0ですが、MSX-DOS 1モードで動作している場合はバンク3）に切り替えた後、アドレス `(CODE_ADD)` にあるルーチンを呼び出します。BASICエラーが発生した際などにカーネルバンクを正しく維持するために CALBAS を呼び出す場合や、F37Dhフックを介してDOSファンクションを呼び出す場合に、このルーチンを使用する必要があります。

```
入力:  (CODE_ADD) に呼び出すコードのアドレスを設定。
       呼び出すルーチンに渡す AF, BC, DE, HL, IX, IY。
出力:  呼び出したルーチンから返された AF, BC, DE, HL, IX, IY。
```

*注意*: `CODE_ADD` のアドレスは `F1D0h` です。

#### 4.2.4. CALBNK (4042h)

他のバンクにあるルーチンを呼び出します。これはドライバが2つ以上のバンクにまたがっている場合に便利であり、また GSLOT1, GWORK, RDBANK などのユーティリティルーチンを使用する際にも必要となります。

```
入力:   A  = バンク番号
        IX = ルーチンのアドレス (ページ1のアドレスである必要があります)
        AF'= 呼び出し先ルーチンへの入力パラメータ
             (呼び出し先ルーチンには AF として渡されます)
        BC, DE, HL, IY = 呼び出し先ルーチンへの入力パラメータ
出力:   AF, BC, DE, HL, IX, IY = 呼び出し先ルーチンからの出力パラメータ
```

#### 4.2.5. GWORK (4045h)

指定されたスロット、または現在ページ1に切り替えられているスロットに対応する、8バイトの `SLTWRK` エントリのアドレスを取得します。この領域の最初の2バイトには、DRV_INITルーチンで要求された、割り当て済みのページ3ワークエリアへのポインタが含まれます（ワークエリアが割り当てられていない場合は0が入ります）。

```
入力:    A  = スロット番号
              (ページ1の現在のスロットを指定する場合は0)
出力:    A  = 現在ページ1に切り替えられているスロット番号 (入力が0の場合)
              変更なし (入力が0以外の場合)
         IX = 指定されたスロットの 8バイト SLTWRK エントリのアドレス
破壊:    F
```

`SLTWRK` 領域とワークエリアの使い方については、[4.4.3. DRV_INIT](#443-drv_init-4136h) の解説を参照してください。

*注意*: このルーチンは直接呼び出すことはできません。以下のように、バンク0へのインターバンク呼び出しを介して呼び出す必要があります。

```
LD A,<スロット番号、または現在のスロットを示す0>
EX AF,AF'
XOR A
LD IX,GWORK
CALL CALBNK
```

#### 4.2.6. K_SIZE (40FEh)

このアドレスには、Nextorカーネルを構成するバンク数（あるいは、ドライバの最初のバンク番号）を示す1バイトの値が格納されています。

ドライバが複数のバンクにまたがり、別のドライババンクにあるデータやルーチンにアクセスする必要がある場合（RDBANK や CALBNK を使用）、固定のバンク番号をハードコーディングするのではなく、`K_SIZE`（または `CUR_BANK` の値）に適切なオフセットを加算してバンク番号を計算してください。このように記述することで、将来のバージョンでNextorカーネルの共通コードバンク数が増加した場合でも、再コンパイルなしでドライバが正常に動作します。

#### 4.2.7. CUR_BANK (40FFh)

このアドレスには、現在のバンク番号を示す1バイトの値が格納されています。最初のドライババンクではこの値は `K_SIZE` と同じになり、追加のドライババンクがある場合は順に1ずつ増加します。

#### 4.2.8. CHGBNK (7FD0h)

これは厳密にはページ0のルーチンではありませんが、すべてのバンクで利用可能です。指定されたバンクをZ80のページ1（4000h〜7FFFh）に表示させます。通常、ドライバコードがこのルーチンを直接使用する必要はなく、代わりに `CALBNK` を使用します。

```
入力:     A = バンク番号
出力:     -
破壊:     AF
```

#### 4.2.9 PROMPT (41E8h)

Nextor 2.1.0 カーネル以降、`PROMPT` ルーチンを呼び出すことで、「Insert disk for drive X: and strike a key when ready」（ドライブX:にディスクを挿入し、キーを押してください）という旨のメッセージを表示し、ユーザーのキー入力を待機させることができます。このルーチンはメインバンクのアドレス `41E8h` で利用可能であり、以下のように [CALLB0](#423-callb0-403fh) を使用して呼び出すことができます。

```
PROMPT:   equ 41E8h
CODE_ADD: equ 0F1D0h
CALLB0:   equ 403Fh

    ld hl,PROMPT
    ld (CODE_ADD),hl
    call CALLB0
```

このルーチンは以下のワークエリアを使用します。

* 対象となるドライブ番号（0ベース：0=A:, 1=B:など）は、アドレス `F33Fh` の `TARGET` から取得されます。
* ルーチンが実行される前に、アドレス `F24Fh` の `H.PROMPT` フックが、0ベースのドライブ番号を A に設定した状態で呼び出されます。

### 4.3. ドライバヘッダー

ドライバヘッダーは、Nextorドライバの先頭部分です。Nextorがドライバを認識し、そのタイプを判断するのに役立つ情報が含まれています。

ヘッダーはドライバが配置される先頭アドレス（4100h）から開始されます。

#### 4.3.1. DRV_SIGN (4100h)

有効なドライバであることを示す署名（シグネチャ）です。起動時にカーネルコードがドライババンクの内容をチェックする際に使用されます。この部分は、すべて大文字のゼロ終端文字列 `"NEXTOR_DRIVER"`（引用符は除く）である必要があります。

#### 4.3.2. DRV_FLAGS (410Eh)

ドライバの機能に関する情報を示すフラグバイトです。

```
bit 0:  0 = ドライブベースドライバ
        1 = デバイスベースドライバ
bit 1:  予約。常に0にしてください。
bit 2:  ドライバが DRV_CONFIG ルーチンを実装している場合は 1。
bit 3-7: 予約。常に0にしてください。
```

なお、`DRV_CONFIG` は Nextor 2.0.5 以降で使用されています。

#### 4.3.3. RESERVED (410Fh)

予約バイトです。常に0にしてください。

#### 4.3.4. DRV_NAME (4110h)

ドライバの名前を示す文字列です。32文字の印字可能ASCII文字（文字コード32から126）で構成されている必要があります。文字列は左詰めにし、右側はスペースで埋めてください。

### 4.4. 共通ルーチン

ドライバヘッダーに続く部分は、すべてのドライバ（ドライブベースかデバイスベースかに関わらず）で実装が必要なルーチン群へのジャンプテーブルです。`DRV_INIT` を除き、これらのルーチンはすべてを実装する必要はなく、大抵はシンプルな `RET` 命令（必要に応じてエラーコードを返す）を配置するだけで十分です。

これらのルーチンでは、データを返すために指定されているレジスタを除き、どのレジスタの値も保存（退避）する必要はありません。この規則は、ドライブベース/デバイスベース専用ルーチンにも同様に適用されます。

#### 4.4.1. DRV_TIMI (4130h)

ドライバのタイマー割り込みルーチンのエントリポイントです。VDPの周波数設定に応じて、1秒間に50回または60回呼び出されます。ドライバでタイマー割り込みを処理する必要がない場合は、このエントリを `RET` 命令で埋めてください。

なお、このエントリは `DRV_INIT` の最初の実行時に出力として `Cy=1` を返した場合にのみ呼び出されます。詳細については、[4.4.3. DRV_INIT](#443-drv_init-4136h) を参照してください。

#### 4.4.2. DRV_VERSION (4133h)

ドライバのバージョンを返します。メジャーバージョン、マイナーバージョン、リビジョン番号の3つを、それぞれ1バイトずつの値で返します。

```
入力:   -
出力:   A = メジャーバージョン
        B = マイナーバージョン 
        C = リビジョン番号
```

#### 4.4.3. DRV_INIT (4136h)

ドライバの初期化ルーチンです。カーネルから以下の2回に分けて呼び出されます。

1. **1回目の実行：情報収集**

```
入力:   A  = 0
        B  = 使用可能なドライブ文字の総数
        HL = 確保可能なページ3ワークエリアの最大サイズ
        C  = 初期化フラグ
             bit 5: ユーザーがドライブ数の削減を要求している場合は 1
出力:   A  = 管理するドライブユニット数（ドライブベースドライバのみ）
        HL = 必要なページ3ワークエリアのサイズ
        C  = 初期化フラグ
             bit 5: ユーザーがドライブ数の削減を要求している場合は 1
        Cy = DRV_TIMI をタイマー割り込みにフックする必要がある場合は 1、そうでない場合は 0
```

2. **2回目の実行：ワークエリアおよびハードウェアの初期化**

```
入力:   A = 1
        B = このコントローラ（ドライバ）に対して実際に割り当てられたドライブ数
```

ドライブベースドライバは、1回目の実行の戻り値 A で、必要なドライブユニット数を返す必要があります。デバイスベースドライバは、オプションで [DRV_CONFIG ルーチン](#448-drv_config-4151h) を実装して、起動時に割り当てるドライブ数を要求し、[自動マッピング処理](Nextor%202.1%20User%20Manual.md#32-booting-nextor) をオーバーライドすることができます。

ユーザーが起動時に「5」のキーを押し続けている場合など、ドライバごとに1つだけのドライブ割り当てを求めている場合に「ドライブ数削減要求」フラグ（Cレジスタのbit 5）がセットされます。将来のNextorのバージョンではこの動作（キー判定など）が変わる可能性があるため、ドライバがキーボードを直接スキャンすることは避け、このフラグを見て動作を決定してください。なお、この同じフラグは [DRV_CONFIG ルーチン](#448-drv_config-4151h) にも渡されます。

このルーチンの2回目の実行以降、`GWORK` ルーチンを呼び出すことで、いつでも `SLTWRK` 内の現在のスロット用に確保された領域のアドレスを取得できます。ページ3ワークエリアに関して、ドライバは以下のように動作する必要があります。

* **必要なサイズが8バイト以下の場合**: 1回目の実行の戻り値として `HL=0` を返します。システムがこのスロットのために `SLTWRK` 内に確保している8バイトの領域自体をワークエリアとして使用します。

```
XOR A
EX AF,AF'
XOR A
LD IX,GWORK
CALL CALBNK
; IX が指す 8バイトの領域をワークエリアとして使用する
```

* **必要なサイズが8バイトを超える場合**: 1回目の実行の戻り値として、必要なサイズを `HL` に返します。システムが確保したメモリへのポインタは、`SLTWRK` エントリの最初の2バイトから取得します。

```
XOR A
EX AF,AF'
XOR A
LD IX,GWORK
CALL CALBNK
LD L,(IX)
LD H,(IX+1)
; HL が指す領域をワークエリアとして使用する
```

また、以下の点に注意してください。

* 1回目の実行時に、利用可能なサイズを超えるページ3ワークエリアを要求した場合、2回目の呼び出しは行われず、ドライブも割り当てられず、タイマー割り込みフックも行われません（Nextorはそのコントローラを無視します）。ワークエリアの要求は常に現実的な制限内に収めてください。
* ドライブベースドライバの場合、管理するユニット数と同じ数のドライブ文字が割り当てられますが、利用可能な文字数を超えるユニットが存在する場合は、割り当て可能な分だけが割り当てられ、初期化自体は通常通り継続されます。これはデバイスベースドライバも同様で、Nextorは通常、これらのドライバに対して2つのドライブを割り当てようと試みます。
* ドライブベースドライバにおいて、管理ユニット数が0であっても、フックを要求していればタイマー割り込みルーチンは呼び出されます（これはMSX-DOSとは異なる挙動です）。

#### 4.4.4. DRV_BASSTAT (4139h)

BASICの拡張命令（「CALL」コマンド）ハンドラのエントリです。標準的なハンドラと同様に動作しますが（詳細は『MSX2 Technical Handbook』などを参照）、処理するコマンドに引数がある場合、MSX BIOSの `CALBAS` ルーチン（BASICインタープリタのヘルパールーチン）を直接呼び出すことはできません。代わりに、ページ0にある [CALLB0 エントリ](#423-callb0-403fh) を介して呼び出す必要があります。

ドライバでBASIC拡張命令をサポートしない場合は、キャリーフラグ（Cy）をセットして `RET` してください。

#### 4.4.5. DRV_BASDEV (413Ch)

BASICの拡張デバイス（`"DEV:"` など）ハンドラのエントリです。動作は標準的なハンドラと同様ですが、`CALBAS` の呼び出しについては [DRV_BASSTAT](#444-drv_basstat-4139h) と同様の注意が必要です。

ドライバで拡張デバイスをサポートしない場合は、キャリーフラグ（Cy）をセットして `RET` してください。

#### 4.4.6. DRV_EXTBIO (413Fh)

拡張BIOS（EXTBIO）ハンドラです。標準的なハンドラと同様に動作しますが、終了時に裏レジスタの D' に、カーネルがその後どのように処理を継続すべきかを示す値を返す必要があります。

```
D'=0: 直ちに呼び出し元へ戻る（RET）。
D'=1: カーネル、またはシステムの標準の拡張BIOSハンドラを実行する。
```

ドライバの拡張BIOSハンドラが呼び出された時点では、常に `D'=1` に設定されています。したがって、ドライバで拡張BIOS呼び出しを一切インターセプトしない場合は、このエントリを単純な `RET` 命令で埋めておくだけで構いません。

#### 4.4.7. DRV_DIRECT0/1/2/3/4 (4142h, 4145h, 4148h, 414Bh, 414Eh)

ドライバへのダイレクト呼び出し用のエントリです。カーネルROM（バンク0またはバンク3）のアドレス `7850h` から `785Ch` までに用意されている5つのエントリポイントへの呼び出しは、それぞれ対応するこの `DRV_DIRECT` エントリポイントにリダイレクトされます。これは、ドライバが独自の追加機能（設定、情報取得など）を提供したい場合に非常に便利です。これらのルーチンが実行される際、呼び出し時のページング状態がそのまま維持されますが、ページ1には当然、カーネルバンクの代わりにドライババンクが切り替わった状態になります。`IX` と `AF'` を除くすべてのレジスタの値は、呼び出し元からそのまま保持されて渡されます。

ドライバでダイレクト呼び出し機能を提供しない場合は、これらのエントリを `RET` 命令で埋めてください。

#### 4.4.8. DRV_CONFIG (4151h)

Nextor 2.0.5 で導入されたこのルーチンは、起動時（ブート時）にドライバの好ましい設定情報をカーネルに伝えるために使用されます。このルーチンを実装する場合、[DRV_FLAGS](#432-drv_flags-410eh) の対応するビット（bit 2）を1に設定する必要があります。

Nextorは、呼び出し時にレジスタ A で「設定インデックス」を指定します。将来のNextorバージョンで新しい設定インデックスが定義される可能性があるため、不明なインデックスが指定された場合や、既知であっても有効な値を返せない場合には、このルーチンは常にエラー（A=1）を返すように記述する必要があります。

設定の提供はすべて任意（オプショナル）です。ドライバは特定の設定だけをサポートし、他をエラーにすることができます。その場合、Nextorはデフォルトの設定、または自動計算された設定値を使用します。

*注意*: 現在定義されているすべての設定は、デバイスベースドライバにのみ適用されます。

```
入力:
  A = 設定インデックス
  BC, DE, HL = 設定インデックスに応じた入力パラメータ

出力:
  A = 0: 正常終了
      1: 指定されたインデックスの設定は利用不可、または不明な設定インデックス
  BC, DE, HL = 設定インデックスに応じた出力パラメータ

* インデックス 1: 起動時の割り当てドライブ数を取得
  入力:
    A = 1
    B = 0 (DOS 2モード時), 1 (DOS 1モード時)
    C = 初期化フラグ
        bit 5: ユーザーがドライブ数の削減を要求している場合は 1
  出力:
    B = ドライブ数

* インデックス 2: 各ドライブのデフォルト設定を取得
  入力:
    A = 2
    B = 0 (DOS 2モード時), 1 (DOS 1モード時)
    C = 起動時におけるドライバ内での相対ドライブ番号
  出力:
    B = デバイスインデックス (1〜7)
    C = LUNインデックス (1〜7)
```

「ユーザーによるドライブ数削減要求」フラグの意味については、[DRV_INIT](#443-drv_init-4136h) の説明を参照してください。

「各ドライブのデフォルト設定を取得」を使用すると、Nextorは起動時に指定されたデバイスおよびLUNを対象ドライブに割り当て、パーティションを自動的に選択します。起動時に対象デバイスの準備ができていない（メディアが挿入されていない等）場合でも、ドライブ自体の割り当ては行われます。アクセスされるたびに、Nextorはデバイスが利用可能になるまでパーティションの検索を試みます。これは、起動時にメディアが挿入されていない可能性のあるリムーバブルメディアドライブを、あらかじめ特定のドライブレターに固定しておくのに便利です。

この「各ドライブのデフォルト設定を取得」は、相対ドライブ番号 0 から `N-1`（`N` は「起動時の割り当てドライブ数を取得」で返された数、あるいはその設定をサポートしていない場合はNextorが接続デバイス数から自動計算した数）の範囲で順に呼び出されます。

#### 4.4.9. RESERVED (4155h から 415Fh)

将来の拡張のために予約されています。すべて0で埋めてください。

## 4.5. ドライブベースドライバ用ルーチン

共通ルーチンに続く部分は、ストレージデバイスにアクセスするためのルーチン群です。ドライブベースドライバとデバイスベースドライバで構成が異なります。本セクションでは、MSX-DOSのディスクドライバとほぼ同様のインターフェースを持つ、**ドライブベースドライバ**に必要なルーチンについて説明します。

ドライブベースドライバは、`0` から `N-1` までの `N` 個のドライブユニットを制御します（`N` は `DRV_INIT` の実行時にドライバが返す値です）。オペレーティングシステムはこれらのユニットに対して個別にドライブ文字を直接割り当てるため、これらのユニットは常に有効なファイルシステム構造を保持している必要があります。外部の設定ツールなどを使用して、ドライブユニットから実際の物理デバイスや特定のパーティションへのマッピングを行う責任は、すべてドライバ側にあります。

#### 4.5.1. DRV_DSKIO (4160h)

指定されたドライブユニットに関連付けられたストレージデバイスの、セクタの読み書きを行います。

```
入力:  A  = ドライブユニット（0から開始）
       Cy = 0（セクタ読み込み時）, 1（セクタ書き込み時）
       B  = 転送するセクタ数
       C  = セクタ番号の上位ビット（bit 22-16）※bit 7がクリアされている場合
            メディア記述子バイト（Media ID） ※bit 7がセットされている場合
       DE = セクタ番号の下位ビット（bit 15-0）
       HL = 転送先 / 転送元のメモリの先頭アドレス

出力:  Cy = 0（成功時）, 1（エラー発生時）
       A  = エラーコード（エラー発生時のみ）:
            0   書き込み禁止（Write protected）
            2   準備未完了（Not ready）
            4   データ(CRC)エラー（Data error）
            6   シークエラー（Seek error）
            8   セクタが見つからない（Record not found）
            10  書き込み障害（Write fault）
            12  その他のエラー（Other errors）
       B  = 実際に転送されたセクタ数（エラー発生時のみ）
```

従来のMSX-DOSドライバとは異なり、Nextorではこのルーチンが「ページ1（4000h〜7FFFh）」のRAM領域を転送先/転送元として呼び出されることはありません。カーネルがデータをページ1へ転送する必要がある場合、自動的に1セクタごとの転送に分割し、ページ3のテンポラリバッファを経由させます。そのため、ドライバコード側でページ1の重複を気にする必要はなく、常にメモリとデバイス間の直接転送を行って構いません。

Nextorが対象ドライブにFAT16ファイルシステムが存在すると判断した場合、レジスタ C はセクタ番号の22〜16ビット目を保持するために使用され、レジスタ CDE を合わせた23ビット値でセクタ番号を扱います。FAT12ドライブである場合は、C の最上位ビット（bit 7）がセットされた状態のメディア記述子（F8h等）になり、セクタ番号は DE の16ビット値となります。

#### 4.5.2. DRV_DSKCHG (4163h)

指定されたドライブユニットに関連付けられたメディアの変更状態を取得します。

```
入力:  A  = ドライブユニット（0から開始）
       B  = C = メディア記述子バイト
       HL = DPBを格納するバッファのアドレス - 1

出力:  Cy = 0（成功時）, 1（エラー発生時）
       A  = エラーコード（エラー発生時のみ、DRV_DSKIOと同じ）
       B  = メディアの状態（成功時のみ）:
            1  前回の呼び出し以降、メディアは変更されていません
            0  不明（判定不能）
            -1 前回の呼び出し以降、メディアは変更されました
```

メディアの状態が「変更された（-1）」または「不明（0）」の場合、本ルーチンは対象メディアのDPB（Drive Parameter Block）を構築し、`HL + 1` のアドレスにコピーする必要があります。DPBのフォーマットについては、[4.5.3. DRV_GETDPB](#453-drv_getdpb-4166h) を参照してください。

#### 4.5.3. DRV_GETDPB (4166h)

指定されたドライブユニットに関連付けられたメディアのDPBを取得します。

```
入力:  A  = ドライブユニット（0から開始）
       B  = C = メディア記述子バイト
       HL = DPBを格納するバッファのアドレス - 1
出力:  -
```

18バイトのDPBのフォーマットは以下の通りです。

```
+00:  メディア記述子バイト（F0h から FFh）
+01:  セクタサイズ（2バイト、2のべき乗である必要があります）
+03:  ディレクトリマスク：(セクタサイズ / 32) - 1
+04:  ディレクトリシフト：ディレクトリマスクの1のビット数
+05:  クラスターマスク：(クラスターあたりのセクタ数) - 1
+06:  クラスターシフト：クラスターマスクの1のビット数 + 1
+07:  最初のFATの開始セクタ番号
+08:  FATの数
+0A:  ルートディレクトリのエントリ数（最大254）
+0B:  データ領域の最初のセクタ番号（2バイト）
+0D:  最大クラスター番号：クラスター数 + 1（2バイト）
+0F:  総セクタ数
+10:  ルートディレクトリの開始セクタ番号
```

構築したDPBを `HL + 1` のアドレスにコピーしてください。

#### 4.5.4. DRV_CHOICE (4169h)

フォーマットメニュー表示用の選択肢文字列を返します。

```
入力:  -
出力:  HL = カーネルスロット内にある選択肢文字列のアドレス
```

このルーチンは、FORMATコマンド実行時、またはCHOICEファンクションコールが呼び出された際に、ユーザーにフォーマットオプションを提示するために呼び出されます。HL に返すべき値は、提示するメニュー文字列（ゼロ終端）のアドレスです。この文字列はカーネルスロット内に存在し、`RDSLT` 等で読み取り可能である必要があります。カーネルのベース部分を変更することなく使用できる、以下の3つの典型的な応答パターンがサポートされています。

1. **フォーマット形式が1種類のみ存在する場合（選択の余地がない場合）**:
   `HL = 0` を返します。
2. **フォーマットをサポートしていない場合（最も一般的なケース）**:
   `HL = 781Fh` を返します。これは、カーネルバンク0および3内に用意されている空の文字列（Null string）のアドレスです。
3. **レガシーなMSXフロッピーディスクドライブのように、1DD / 2DD の選択を提示する場合**:
   `HL = 7820h` を返します。これは、カーネルバンク0および3内に用意されている "Single sided / Double sided" という文字列のアドレスです。

これら以外の独自のカスタム文字列を返す場合は、カーネルメインバンクにある空き1Kスペースに文字列を配置する必要があります。詳細については、「[4.7.1. カーネルメインバンクの空きスペース](#471-カーネルメインバンクの空きスペース)」を参照してください。

#### 4.5.5. DRV_FORMAT (416Ch)

ディスクを物理フォーマットし、ブートセクタ、FAT、ルートディレクトリの各領域を初期化します。

```
入力:  A  = ユーザーが選択したフォーマット形式（1〜9、DRV_CHOICE で表示された順）
       D  = ドライブユニット（0から開始）
       HL = 処理用の作業用RAMエリアのアドレス
       DE = 作業用RAMエリアのサイズ

出力:  Cy = 0（成功時）, 1（エラー発生時）
       A  = エラーコード（エラー発生時のみ）:
            0   書き込み禁止（Write protected）
            2   準備未完了（Not ready）
            4   データ(CRC)エラー（Data error）
            6   シークエラー（Seek error）
            8   セクタが見つからない（Record not found）
            10  書き込み障害（Write fault）
            12  無効なパラメータ（Bad parameter）
            14  メモリ不足（Insufficient memory）
            16  その他のエラー（Other errors）
```

このルーチンは、`DRV_CHOICE` をもとにユーザーが選択したフォーマットオプション（レジスタ A）に従って、実際の物理フォーマット処理とファイルシステム初期化を行います。

HL で渡される作業エリアは、フォーマット処理中に自由に一時バッファとして利用して構いません。

#### 4.5.6. DRV_MTOFF (416Fh)

管理しているすべてのドライブのモーターを停止させます。これは主にフロッピーディスクドライブにのみ関係する処理であり、それ以外のデバイス（フラッシュメモリメディアなど）を扱うドライバでは、何もせずに単に `RET` してください。このルーチンには入力・出力パラメータはありません。

## 4.6. デバイスベースドライバ用ルーチン

本セクションでは、**デバイスベースドライバ**に必要なデバイスアクセス用のルーチンについて説明します。これらのエントリポイントは、ドライブベースドライバのルーチンと同じアドレス（ジャンプテーブルの同じスロット）を共有しています。ドライバはどちらか一方のスタイル（ドライブベースかデバイスベースか）のみを実装するため、これで問題ありません。

デバイスベースドライバでは「ドライブユニットをドライブレターに一対一で固定する」という方法をとらず、最大7つまでの物理「デバイス（Devices）」を直接オペレーティングシステムに開示します。個々のデバイスや、デバイス内の各パーティションに対するドライブ文字の割り当て（マッピング）は、すべてNextorカーネル自身が自動的に、またはユーザー指定（MAPDRVコマンドなど）に従って処理します。

ドライバが制御する各物理デバイスには、`1` から `7` までの「デバイスインデックス」が割り当てられます。さらに、各デバイスには `1` から `7` までの「論理ユニット（LUN: Logical Unit）」を持たせることができます（たとえば、複数のスロットを持つマルチカードリーダーであれば、個々のスロットを論理ユニットとして定義できます）。物理的にデバイスが1つのメディアしか持たない場合（これが最も一般的です）は、論理ユニットの総数を `1` とし、常に論理ユニット番号 `1` としてアクセスさせます。

#### 4.6.1. DEV_RW (4160h)

デバイスに対して絶対セクタの読み書きを行います。

```
入力:  Cy = 0（セクタ読み込み時）, 1（セクタ書き込み時）
       A  = デバイスインデックス（1〜7）
       B  = 転送するセクタ数
       C  = 論理ユニット（LUN）番号（1〜7）
       HL = 転送先 / 転送元のアドレス（ページ1以外のメモリ空間）
       DE = 4バイトの開始セクタ番号（32ビット値）が格納されている、ページ1以外のメモリ空間のアドレス

出力:  A  = エラーコード:
            0: 正常終了
            .IDEVL (B5h): 無効なデバイス、または無効なLUN
            .NRDY  (C4h): 準備未完了（Not ready）
            .DISK  (C7h): 一般的なディスクエラー
            .DATA  (C8h): 読み込み時のCRCデータエラー
            .RNF   (C9h): セクタが見つからない（Record not found）
            .UFORM (CAh): メディアが未フォーマット
            .WPROT (CBh): 書き込み禁止（またはLUNが読み取り専用）
            .WRERR (CCh): 書き込みエラー
            .NCOMP (CDh): 互換性のないディスク
            .SEEK  (D0h): シークエラー
       B  = 実際に読み書きされたセクタ数（エラー発生時のみ）
```

このルーチンは、デバイスとの間で直接セクタアクセスを行うために使用されます。ここで読み書きする対象は**物理的なデバイスの絶対セクタ**であり、特定のパーティションにおける相対セクタではありません。ドライバ自身は、パーティション分割に関する情報を一切関知する必要はありません。

アクセス開始セクタ番号は、レジスタ DE が指すメモリ位置に配置された32ビット（4バイト）値として渡されます。DE や HL が指すメモリアドレスは、常に「ページ1以外」であることが保証されているため、ドライバ側でページ切り替えのコンフリクトを心配することなく、直接メモリにアクセスしてデータを転送できます。

指定されるセクタ番号は、`0` から、`LUN_INFO` が返す「最大セクタ数 - 1」の範囲になります。`LUN_INFO` が最大セクタ数を `0` として返したデバイスについては、扱えるセクタの範囲は不定となり、ドライバの仕様に依存します。

このルーチンはすべてのブロックデバイスに対して正しく機能する必要があります。非ブロックデバイス（キャラクタデバイス等）であっても、セクタ単位での読み書きをエミュレートできるのであれば、任意で動作させることができます。

ここで返すエラーコードは、MSX-DOS 2で規定されている「ディスクエラー」のコードと同じです。ただし、`.IDEVL`（B5h、無効なデバイス/LUN）はNextorで新しく定義されたエラーです。Nextorで追加された新しいエラーの一覧は、*『Nextor 2.1 プログラマーズリファレンス』*を参照してください。

#### 4.6.2. DEV_INFO (4163h)

指定されたデバイスに関する情報、または名前などのテキスト情報を取得します。

```
入力:  A  = デバイスインデックス（1〜7）
       B  = 取得したい情報の種類:
            0: 基本情報 (Basic information)
            1: 製造元名文字列 (Manufacturer name string)
            2: デバイス名文字列 (Device name string)
            3: シリアル番号文字列 (Serial number string)
       HL = 情報を格納するバッファのアドレス（ページ1以外のメモリ空間）

出力:  A  = エラーコード:
            0: 正常終了
            1: デバイスが利用不可能、該当する情報がない、
               または指定された情報の種類（B）が無効
```

カーネルは、接続されているデバイスの状態確認や、情報の取得のためにこのルーチンを呼び出します。「基本情報（B=0）」の返却は必須であり、デバイスが存在しない場合以外はエラーを返してはなりません。その他の文字列情報（B=1〜3）についてはオプショナル（任意）であり、用意できない場合はエラー（A=1）を返して構いません。

HL が指すバッファアドレスは「ページ1以外」であることが保証されているため、ドライバはページ切り替えを気にすることなく直接バッファにデータを書き込めます。

**基本情報（B=0）**を要求された場合、ドライバは HL の指すアドレスに以下のフォーマットで2バイトのデータを書き込む必要があります。

```
+0 (1): 論理ユニット（LUN）の数。1 から 8 までの値。
        論理ユニットが区別されない、あるいは1つだけの場合は 1。
+1 (1): デバイス機能フラグ。現在のバージョンでは 0 固定にする必要があります。
```

その他の情報（B=1〜3）は、すべてテキスト文字列の形式で返します。文字列は印字可能なASCIIコード（32から126まで）のみで構成し、左詰めにし、既定の長さに満たない場合はスペースで右パディングしてください。

もしデバイス自身が情報をバイナリ形式で保持している場合は、上位大文字の16進数表記にし、先頭に `"0x"` というプレフィックスを付与した文字列として返してください。

文字列の最大長さは **64文字** です。元の名前がこれより長い場合は、左側の64文字を切り出して返してください。

シリアル番号文字列（B=3）についても上記と同様の規則が適用されますが、シリアル番号だけは **右詰め** で返し、長すぎる場合は左側を切り捨てて「右側の最大64文字」を返すようにしてください。

同じシステムに接続された異なる2つのデバイスに対して、製造元名・デバイス名・シリアル番号の組み合わせが全く同一になるような返し方は避けてください。ドライバ内にハードコーディングされた固定のシリアル番号を返すことは推奨されません。デバイス本体から固有のシリアル番号を取得できない場合は、シリアル番号は提供せず、エラー（A=1）を返してください。

#### 4.6.3. DEV_STATUS (4166h)

指定されたデバイス、または特定の論理ユニットの接続状態およびメディア変更状態を取得します。

```
入力:  A = デバイスインデックス（1〜7）
       B = 論理ユニット（LUN）番号（1〜7）
           0 を指定した場合は、デバイスそのもののステータスを要求

出力:  A = 指定されたLUN、またはデバイスそのもののステータス（B=0の場合）:
            0: 対象のLUN、またはデバイスが利用不可能。または指定された番号が無効。
            1: 利用可能。かつ、前回のステータス要求以降メディアは変更されていません。
            2: 利用可能。かつ、前回のステータス要求以降にメディア変更がありました。
               （B=0でデバイス自体のステータスを返す場合、同じインデックスに対して
                デバイスの抜差し（ホットプラグ）が行われたことを示します。
                LUNを対象とする場合は、メディア（SDカードやCD等）の変更を示します。）
            3: 利用可能だが、前回の要求以降にメディアが変更されたかどうかを
               ドライバ側で判定することができません。
```

このルーチンは、接続メディアの変更（ディスクチェンジ）をオペレーティングシステムが検知するために呼び出されます。Nextorは通常、`LUN_INFO` で「リムーバブルメディア（removable）」フラグがセットされている論理ユニットに対してのみ、定期的にこのルーチンを呼び出します。ただし、MSX-DOS 1互換モードで動作している場合に限り、固定メディア（ハードディスクなど）に対しても呼び出されることがあります（この場合、ドライバは常に `0` または `1` を返すようにしてください）。

現在のNextorバージョンでは、`B=0`（デバイスそのものの変更チェック）を指定してこのルーチンが呼び出されることはありません。USBバスのようなデバイスのホットプラグ（活線挿抜）の本格的なサポートは、将来のバージョンで計画されています。

ドライバが `A=3`（判定不能）を返した場合、Nextorはアクセス時にブートセクタのチェックサムなどを比較してソフトウェア的にメディア変更を管理します（詳細は『Nextor 2.1 ユーザーズマニュアル』の「メディア変更の管理」を参照）。ただし、余計なディスクリードやチェックサム計算のオーバーヘッドを防ぐために、可能な限りドライバ側でメディア変更を自前で正しく検知し、`1` または `2` を返すように実装することが強く推奨されます。

**極めて重要な注意事項**: ここで報告するステータス（特に「メディア変更あり（2）」）は、**前回のステータス要求の呼び出し時点との対比**である必要があります。途中で `DEV_RW` ルーチンによる読み書きが行われたからといって、変更フラグを内部でクリアしてしまい、その後の `DEV_STATUS` 呼び出しで「変更なし（1）」を返すような実装にしてはなりません。すなわち、「メディアが変更された ➔ その後に `DEV_RW` が実行された ➔ その後に `DEV_STATUS` が呼ばれた」というシナリオにおいても、最後の `DEV_STATUS` は必ず `2` を返す必要があります。この動作は、Nextorのドライブマッピングエンジンが正しくメディア変更を追いかけるために不可欠です。

システム起動直後（`DRV_INIT` 実行後）の最初の呼び出しで返す値は、デバイスが利用可能であれば `1` と `2` のどちらであっても構いません。

#### 4.6.4. LUN_INFO (4169h)

指定された論理ユニット（LUN）に関する詳細情報を取得します。

```
入力:  A  = デバイスインデックス（1〜7）
       B  = 論理ユニット（LUN）番号（1〜7）
       HL = 情報を格納するバッファのアドレス（ページ1以外のメモリ空間）

出力:  A  = 0: 正常終了。バッファに情報が書き込まれました。
            1: エラー。指定されたデバイスまたはLUNが利用不可能、
               または番号が無効。
```

指定された論理ユニットが備える物理的な属性を、HL が指すバッファに返します。HL が指すバッファはページ1以外の領域であることが保証されているため、ページ切り替えに配慮する必要はありません。

バッファには、以下の構造を持つ **12バイト** のデータを書き込みます。

```
+0 (1): メディアタイプ（Medium type）:
        0: ブロックデバイス（一般的なメディア）
        1: CD または DVD リーダー / ライター
        2-254: 未使用（将来の拡張用に予約）
        255: その他のメディア
+1 (2): セクタサイズ（バイト数）。利用できない、または該当しない場合は 0。
+3 (4): 利用可能な総セクタ数。利用できない、または該当しない場合は 0。
+7 (1): 論理ユニット機能フラグ:
        bit 0: メディアが「リムーバブル（取り外し可能）」である場合は 1。
        bit 1: メディアが「読み取り専用（Read only）」である場合は 1。
        bit 2: 論理ユニットが「フロッピーディスクドライブ」として振る舞う場合は 1。
        bit 3: この論理ユニットを「自動マッピング（Automapping）」の対象から
               除外する場合は 1。
        bit 4-7: 未使用。常に0にしてください。
+8 (2): シリンダ数
+10 (1): ヘッド数
+11 (1): トラックあたりのセクタ数
```

「ブロックデバイス」とは、セクタ番号を指定してランダムに読み書き可能なすべてのストレージデバイス（フロッピーディスク、ハードディスク、CF/SDカード、USBメモリなど）を指します。これらは `DEV_RW` ルーチンによってセクタ単位でアクセスできる必要があります。

現行バージョンのNextorは、メディアタイプが「ブロックデバイス（0）」であり、かつセクタサイズが「512バイト」と報告されたデバイスとのみ動作します。その他のセクタサイズや非ブロックデバイスへの直接的なファイルシステムアクセスのサポートは、将来のバージョンで計画されています。

シリンダ数、ヘッド数、トラックあたりセクタ数のパラメータは、主に（レガシーな）ハードディスクドライブにのみ関係する項目です。該当しない場合や情報が得られない場合は、すべて `0` を返してください。Nextorカーネル自身はこれらのCHS情報を利用しませんが、パーティション分割ツールなどが境界を揃える（アライメント調整する）ために参照することがあります（現在のNextorに内蔵されているパーティションツールでは使用していません）。

「読み取り専用」フラグは、CD-ROMメディアなどのように、ハードウェアの基本設計レベルで書き込みが不可能なデバイスに対してのみセットしてください。単にSDカードの書き込み禁止スイッチがONにされているような、動的に変化する状態に対してこのフラグを立てるべきではありません。

現在のバージョンのNextorでは、デバイスベースのドライバに繋がれたデバイスをフォーマットすることはサポートされていません。これは将来のバージョンで計画されている機能であり、その際には「フロッピーディスクドライブ（bit 2）」フラグがセットされたデバイスに対してのみフォーマットが提供される予定です。

## 4.7. その他

Nextorデバイスドライバの設計に関する、その他の有益な情報です。

### 4.7.1. カーネルメインバンクの空きスペース

Nextorカーネルの2つのメインバンク（通常モードで動作しているときの「バンク0」と、MSX-DOS 1互換モードで動作しているときの「バンク3」）には、それぞれ共通して **1Kバイトの未使用領域** があります。この領域は、ドライバが自由に使用できる共通のコードやデータの格納スペースとして公開されています。

メインバンクは、システムの実行中、通常のコンテキストにおいてカーネルスロットに永続的にマップされています（他のバンクは、一時的な呼び出しの際にのみ瞬時に切り替えられます）。したがって、この1K領域（アドレス `7BD0h` から `7FCFh`）に配置されたコードやデータは、Nextor独自のバンク切り替えの仕組みを知らない外部のユーザープログラムからでも、スロット切り替えのみ（`CALSLT` や `RDSLT` など）で直接、容易に読み書き・実行することが可能です。

主に以下のようなケースで、このフリースペースに独自のコンテンツを配置する必要があります。

* `DRV_CHOICE` や `DRV_FORMAT` において、カーネル標準の文字列（Null文字列や1DD/2DD選択文字列）以外の、**オリジナルのフォーマット形式選択文字列**を表示したい場合。カーネルに予め用意されていない独自のテキストデータは、この空きスペースに配置しておく必要があります。
* 外部のユーティリティアプリケーションが、`RDSLT` などを用いてドライバから特定の情報（たとえば、ドライバが実装している独自のAPIやUNAPIの署名情報など）を直接読み取りたい場合。
* タイマー割り込みや拡張BIOS以外の、システムに存在するその他のBIOSフックなどを直接パッチしたい場合。フックが呼び出す中継コード（トラポリンコード）をこのメインバンク領域に記述しておき、そこからドライババンクへインターバンク呼び出し（`CALBNK`）を行う構造にします。

この領域に配置したコードからドライババンク内のコードを呼び出す場合、ターゲットとなるドライババンク番号は `K_SIZE`（40FEh）のアドレスから読み取って計算することができます。

*注意*: この領域にデータを配置する場合、Nextorの通常モードとMSX-DOS 1互換モードのどちらの状態で実行されても正しく動作するよう、**バンク0とバンク3の双方に、同一の内容を複製して配置する**必要があります。MKNEXROMツールにこの領域用のバイナリファイルを指定して結合すれば、自動的に両方のバンクに同じデータを正しく書き込んでくれます。

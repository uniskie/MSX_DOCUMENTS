## 1. はじめに

Nextorは、MSXコンピュータ用ディスクオペレーティングシステムであるMSX-DOS 2の拡張版です。MSX-DOS 2.31をベースにしており、同バージョンとの互換性を備えています。

本書は、NextorがMSX-DOS 2に対して開発者視点で追加した新機能（主に提供される新しい関数呼び出しや、その他の有用な情報）について解説します。Nextor用のデバイスドライバー開発については本書の対象外です。これについては、別のドキュメントである『Nextor 2.1 Driver Development Guide』で解説しています。

本書は、読者がMSX全般およびMSX-DOS 2（具体的には『MSX2テクニカルハンドブック』の第3章、ならびに『MSX-DOS 2 Program Interface Specification』および『MSX-DOS 2 Function Codes Specification』に記載されている内容）の開発経験、知識を有していることを前提としています。また、本書を読み進める前に『Nextor 2.1 User Manual』をご一読いただくことを推奨します。

## 2. 既存の関数呼び出しにおける変更点

本セクションでは、MSX-DOS 2にすでに存在していた関数呼び出しのうち、Nextorで変更が加えられた点について説明します。関数 `_DPARM` における16ビットセクター数に関する軽微な仕様変更を除き、すべての変更は後方互換性を保っています。

ここではNextorで導入された変更点のみを説明し、各関数の詳細な仕様は省略します。これらの関数呼び出しのより完全な情報については『MSX-DOS 2 Function Codes Specification』を参照してください。

### 2.1. _STROUT (09h)

高速STROUTモードが有効な場合、出力可能な文字列の最大長は511文字に制限されます。これを超える長さの文字列を指定した場合、最初の511文字のみが出力されます。高速STROUTモードはデフォルトで無効になっており、新設された関数 `_FOUT` を使用して明示的に有効にする必要があります。

### 2.2. _ALLOC (1Bh)

対象ドライブで「縮小アロケーション情報モード」が有効な場合、この関数は、合計クラスター数および空きクラスター数に（セクター/クラスター数を乗算した結果が32MB以下となるような）擬似的な値を返します。この縮小アロケーション情報モードは、デフォルトではすべてのドライブで無効になっており、新設された関数 `_RALLOC` を用いてドライブごとに明示的に有効にする必要があります。

さらに、Nextor 2.0.3以降では、環境変数 `ZALLOC` に `ON`（大文字小文字は区別されません）を設定することで、縮小アロケーション情報モードを「ゼロアロケーション情報モード」に切り替えることができます。この環境変数が存在する場合、縮小アロケーション情報モードが有効なすべてのドライブにおいて、`_ALLOC` は空きクラスター数として0を返します。

### 2.3. _RDABS (2Fh) と _WRABS (30h)

これらの関数は、アクセス先ドライブがFAT12ファイルシステムである場合のみ動作します。FAT16ファイルシステムや未知のファイルシステムを持つドライブにアクセスしようとした場合は、「Not a DOS disk」エラーが返されます。

厳密に言えば、MSX-DOSではFAT12のみがサポートされていたため、これはMSX-DOSの挙動からの変更ではありません。しかし、MSX-DOS環境でFAT16ファイルシステムが書き込まれたドライブを読み込もうとすると、そのブートセクターがFAT12のブートセクターと誤認され、関数呼び出し自体は成功してしまいます。Nextorでは、これらの関数によるFAT16へのアクセスを明示的に拒否します。これは、FAT12を前提として低レベルのドライブ処理を行うCHKDSKやIMPROVEなどのプログラムが誤って実行された際に、データの破損を引き起こすのを防ぐための意図的な仕様変更です。

新規に開発するアプリケーションでは、32ビットのセクター数を指定可能で、ファイルシステムの種類を問わずドライブにアクセスできる新しい関数 `_RDDRV` および `_WRDRV` を使用してください。

### 2.4. _DPARM (31h)

この関数は、返却されるパラメータブロックの +24〜27バイト目に、総論理セクター数を32ビット値として返すようになりました。なお、この値が65535を超える場合、+9, 10バイト目に返却される16ビットのセクター数は0になります。

また、返却されるパラメータブロックの +28バイト目には、以下のようにファイルシステムの種類が格納されます。

```
0: FAT12
1: FAT16
255: その他
```

※現在、Nextorが処理できるのはFAT12およびFAT16ファイルシステムのみです。

### 2.5. _DEFER (64h)

ディスクエラー時にユーザー定義ルーチンに渡されるパラメータが、32ビットのセクター数をサポートするように拡張されました。MSX-DOS 2におけるこれらのパラメータの一部は以下の通りでした。

```
C:b3 - セクター番号が有効な場合にセット
DE = セクター番号（Cのb3がセットされている場合）
```

Nextorでは、これらのパラメータは以下のようになります。

```
C:b3 - セクター番号が有効であり、かつ16ビットに収まる場合にセット（すなわち、b4がセットされており、かつHL=0の場合）
C:b4 - セクター番号が有効な場合にセット
HL:DE = セクター番号（Cのb4がセットされている場合）
```

### 2.6. _EXPLAIN (66h)

環境変数 `ERRLANG` に `EN` が設定されている場合（コマンドインタプリタのプロンプトから `SET ERRLANG=EN` を実行）、漢字モード（BASICインタプリタから `CALL KANJI` を実行）がアクティブであっても、この関数は英語のエラーメッセージを返します。この機能はNextor 2.0.4以降で利用可能です。

### 2.7. _FORMAT (67h)

MSX-DOS 2において、この関数はFFhとFEhという2つの特殊な選択パラメータを受け付けます。これらはディスクを実際にフォーマットするのではなく、ディスクのメディアIDに基づいて、ディスクパラメータを含むMSX-DOS 2のブートセクターを生成するものです。この機能は、FIXDISKプログラムが古いMSX-DOS 1形式のディスクをMSX-DOS 2形式に変換する際などに使用されます。

Nextorでは、これに加えて新しく3つの選択パラメータを追加しました。

* FDh: ディスクがFAT12またはFAT16ファイルシステムであり、ブートセクターに有効なディスクパラメータが含まれていることを前提として（そうでない場合は「Not a DOS disk」エラーが返されます）、(1) 製造元名を "NEXTOR" に設定し、(2) 拡張ブロック（29hバイト、およびボリュームID、ボリューム名、"FAT12" または "FAT16" マーク）を生成して、ディスク用の標準ブートセクターを構築します。この際、ディスクパラメータ自体は変更されません。すでに拡張ブロックが存在している場合は、製造元名のみが変更されます（既存のボリュームIDは保持されます）。この選択肢は、他システムでフォーマット済みのディスクに対してダーティディスクフラグ機能を使用する場合に便利です。

* FCh: FDhと同様ですが、ディスクのファイルシステムがFAT12の場合、標準ブートセクターの代わりにMSX-DOS 2互換のブートセクター（"VOL_ID" 文字列を含む）を構築します。FAT16の場合はFDhと同様に機能します。この選択肢は、構築したディスクをMSX-DOS 2システムで使用する場合に有用です。

* FBh: ディスクの「クイックフォーマット」を実行し、FAT領域およびルートディレクトリ領域のみをクリアします。他の2つの新しい選択肢と同様に、ディスクに有効なFAT12またはFAT16のブートセクターが存在している必要があります。そうでない場合は「Not a DOS disk」エラーが返されます。

ディスクが実際にフォーマットされる場合（選択パラメータ 1〜9）は、常にMSX-DOS 2形式のブートセクターが生成されます。

### 2.8. _DOSVER (6Fh)

この関数呼び出しは、実行中のオペレーティングシステムがMSX-DOS 2なのか、あるいはNextor（通常モードまたはMSX-DOS 1モード）なのかをアプリケーション側で検出できるように拡張されています。同時に、従来のMSX-DOSを期待するアプリケーションに対しても正常に動作するよう配慮されています。

Nextorを検出する手順は以下の通りです。アプリケーションは、入力パラメータに以下の「マジックナンバー」を設定して `_DOSVER` 関数を呼び出します。

```
B = 5Ah
HL = 1234h
DE = ABCDh
IX = 0
```

オペレーティングシステムがMSX-DOS 2の場合、この関数は IX = 0 を返します（MSX-DOSは、戻り値を返す場合を除きIXおよびIYレジスタを変更しないため、またこの関数ではこれらのレジスタに戻り値を返さないためです）。Nextor環境でマジックナンバーを指定せずに呼び出した場合も、MSX-DOS 2との互換性を保つために、IXおよびIYは変更されずにそのまま返されます。

Nextor環境において、上記のマジックナンバーを指定して呼び出すと、以下の情報が返されます。

```
B = エミュレートされているMSX-DOSカーネルのメジャーバージョン（常に2）
C = エミュレートされているMSX-DOSカーネルのマイナーバージョン（常に31h）
D = NEXTOR.SYSのメジャーバージョン（BCD形式）
E = NEXTOR.SYSのマイナーバージョン（BCD形式）
HL = カーネルROM内にある、オペレーティングシステム説明文字列のアドレス
IXh = 1
IXl = Nextorメジャーバージョン番号 (2-15)
IYh = Nextorセカンダリバージョン番号 (0-15)
IYl = Nextorリビジョン番号 (0-255)
```

Nextor対応アプリケーションにおけるオペレーティングシステムの判定手順は、以下の通りとなります。

1. マジックナンバーを設定して `DOSVER` 関数を呼び出します。
2. エラー（A <> 0）が発生した場合、OSはMSX-DOSでもNextorでもありません。
3. B < 2 の場合、OSはMSX-DOS 1です。
4. IX が 0 の場合、OSはMSX-DOS 2です。BおよびCレジスタからバージョン番号を取得してください。
5. IXh が 1 の場合、OSはNextorです。IXl、IYh、IYlレジスタからバージョン番号を取得してください。
6. IXh が 0 でも 1 でもない場合、OSはMSX-DOSでもNextorでもありません。

HLに返される値は、実行中のオペレーティングシステムを表すゼロ終端の印字可能文字列（例: "Nextor kernel version 2.0"）へのポインタです。この文字列はカーネルのマスタースロット（スロット番号は 0F348h から取得可能）に配置されており、標準的な `RDSLT` 呼び出しを介して読み取ることができます。

#### 2.8.1 MSX-DOS 1モードでのNextorの検出

`DOSVER` 関数はMSX-DOS 1モードでも利用可能になっており、このモード下でもNextorを検出できます。

MSX-DOS 1モードで `DOSVER` を呼び出した際の返却値は通常モード時と同様ですが、BC = 0100h となり、HLには意味のある値は返されません。また、このモードでは 0F37Dh のフック（『[3. 新規関数呼び出し](#3-新規関数呼び出し)』参照）を経由してのみ呼び出しが可能なため、インデックスレジスタの値が破壊されます。そのため、「IX = 0 であるかをチェックする」手法はNextorの検出には使用できません。その代わり、MSX-DOS 1モードでNextorが実行されている場合、`DOSVER` は A = 1 を返します。

したがって、アプリケーションがMSX-DOS 1モードで動作可能であり、かつそれがNextor環境であるか古いMSX-DOS 1カーネル環境であるかを判別したい場合の手順は以下のようになります。

1. 通常モードと同様に、レジスタにマジックナンバーを設定します。
2. `0005h` エントリポイントではなく、`F37Dh` エントリポイントを介して `DOSVER` 関数を呼び出します。
3. A=1、B=1、かつ IXh=1 であれば、MSX-DOS 1モードでNextorが動作しています。IXl、IYh、および IYl レジスタからNextorのバージョン番号を取得してください。
4. それ以外の場合は、前セクションで説明した通常モード用の手順に従ってください。

## 3. 新規関数呼び出し

本セクションでは、Nextorで新たに導入された関数呼び出しの詳細を説明します。これらは既存のMSX-DOS呼び出しと同様に、Cレジスタに関数番号を設定し、`0005h` または `F37Dh` を呼び出すことで実行されます。各関数に指定されている短縮名（例: `_FOUT`）は、コード内で関数を指し示すための推奨名称であり、本書における相互参照でも使用されています。

新しい関数呼び出しの一部は、MSX-DOS 1モードでも呼び出すことができます。現在のバージョンにおいてこれに該当するのは、`GDRVR`、`GPART`、`CDRVR`、`GDLI` です。MSX-DOS 1モードから呼び出す場合、Nextorのすべての新規関数呼び出しにおいて以下の制限が適用されます。

* 必ず `F37Dh` エントリポイントを使用する必要があります。Nextor用の特別な `MSXDOS.SYS` は存在しないため、`0005h` エントリポイントはサポートされません。

* RAM内のバッファを用いてアプリケーションプログラムとデータをやり取りする場合、そのバッファをページ1（アドレス 4000h〜7FFFh）に配置することはできません。

また、一部の関数には個別に追加の制限事項があります。詳細は各関数の説明を参照してください。

### 3.1. 高速STROUTモードの取得/設定 (_FOUT, 71h)

```
パラメータ:  C = 71H (_FOUT)
             A =  00H => 高速STROUTモードの取得
                  01H => 高速STROUTモードの設定
             B =  00H => 無効化（A=01Hの場合のみ）
                  FFH => 有効化（A=01Hの場合のみ）

結果:        A = エラー
             B = 現在の高速STROUTモード
```

この関数は、高速STROUTモードの有効/無効を切り替えます。このモードが有効な場合、`_STROUT` および `_ZSTROUT` 関数がより高速に動作しますが、出力可能な文字列の最大長は511文字に制限されます。これを超える長さの文字列を指定した場合、最初の511文字のみが出力されます。

### 3.2. ゼロ終端文字列の出力 (_ZSTROUT, 72h)

```
パラメータ:  C = 72H (_ZSTROUT)
             DE = 文字列のアドレス

結果:        A = 0（エラーを返すことはありません）
```

DEで指定されたアドレスにあるゼロ終端（Null終端）文字列を画面に出力します。この関数は高速STROUTモードの影響を受けます。

### 3.3. ドライブからの絶対セクター読み込み (_RDDRV, 73h)

```
パラメータ:  C = 73H (_RDDRV)
             A = ドライブ番号 (0=A: 等)
             B = 読み込むセクター数
             HL:DE = セクター番号

結果:        A = エラーコード (0 => エラーなし)
```

ドライブからセクターを直接読み込みます。`_RDABS` とは異なり、この関数はドライブ上のファイルシステム（FAT12、FAT16、あるいは未知のファイルシステム）の種類に関わらず、またファイルシステムが一切存在しない場合であっても、直接セクターを読み出すことができます。

セクターは、現在のディスク転送アドレス（DMA）に読み込まれます。ディスクエラーが発生した場合は、通常の手順でシステムによって報告されます。

### 3.4. ドライブへの絶対セクター書き込み (_WRDRV, 74h)

```
パラメータ:  C = 74H (_WRDRV)
             A = ドライブ番号 (0=A: 等)
             B = 書き込むセクター数
             HL:DE = セクター番号

結果:        A = エラーコード (0 => エラーなし)
```

ドライブへセクターを直接書き込みます。`_WRABS` とは異なり、この関数はドライブ上のファイルシステムの種類に関わらず、またファイルシステムが一切存在しない場合であっても、直接セクターを書き込むことができます。

セクターは、現在のディスク転送アドレス（DMA）から書き込まれます。ディスクエラーが発生した場合は、通常の手順でシステムによって報告されます。

### 3.5. 縮小アロケーション情報モードベクトルの取得/設定 (_RALLOC, 75h)

```
パラメータ:  C = 75H (_RALLOC)
             A =  00H => 現在のベクトルを取得
                  01H => ベクトルを設定
             HL = 新しいベクトル（A=01Hの場合のみ）

結果:        A = 0（エラーを返すことはありません）
             HL = 現在のベクトル
```

縮小アロケーション情報モードベクトルを取得または設定します。このベクトルの各ビットは各ドライブに対応しています（Lレジスタのビット0がA:、ビット1がB:、等）。ビットが1の場合、そのドライブの縮小アロケーションモードが有効（取得時）または有効に設定（設定時）され、0の場合は無効であることを示します。

### 3.6. ドライブ容量情報の取得 (_DSPACE, 76h)

```
パラメータ:  C = 76H (_DSPACE)
             E = ドライブ番号 (0 = デフォルト, 1 = A: 等)
             A =  00H => 空き容量の取得
                  01H => 総容量の取得

結果:        A = エラーコード
             HL:DE = 容量（キロバイト単位）
             BC = 端数バイト（バイト単位）
```

ドライブの総容量または空き容量を返します。`HL:DE` に返される容量情報は、対象ドライブにマップされているファイルシステムの種類やクラスターサイズに関わらず、常にキロバイト単位となります。

「端数バイト（BCレジスタ）」は、ドライブの最小アロケーション単位（クラスターサイズ）が1KBの倍数になっていない場合にのみ、ゼロ以外の値になります。FATドライブの場合、この値が非ゼロ（具体的には512）になるのは、ドライブの「1クラスターあたりのセクター数」が1で、かつクラスター数が奇数の場合のみです。例えば、1セクター/クラスターで15個の空きクラスターを持つドライブに対して `A=0` でこの関数を呼び出した場合、HL=0、DE=7、BC=512 が返されます。

この関数が返す容量情報は常に実際の値であり、縮小アロケーション情報モードやゼロアロケーション情報モードの影響を受けません。

### 3.7. ドライブのロック/アンロック、またはロック状態の取得 (_LOCK, 77h)

```
パラメータ:  C = 77H (_LOCK)
             E = 物理ドライブ (0=A:, 1=B: 等)
             A =  00H => ロック状態の取得
                  01H => ロック状態の設定
             B =  00H => ドライブのアンロック（A=01Hの場合のみ）
                  FFH => ドライブのロック（A=01Hの場合のみ）

結果:        A = エラーコード
             B = 現在のロック状態（入力時と同様）
```

ドライブをロック/アンロック、あるいは現在のロック状態を取得します。ドライブがロックされると、Nextorはそのドライブのメディアが変更されないものとみなし、関連するドライバーに対してメディアチェンジ状態の問い合わせを行わなくなります。これにより、メディアアクセス全体の速度が向上します。これは、マルチメディアカードなどの着脱式デバイスをメインストレージとして使用する場合に便利です。

ドライブをロックするには、そのドライブが有効なファイルシステムにマップされている（アクセス可能である）必要があります。そうでない場合はエラーが返され、ドライブはロックされません。

一度ドライブがロックされると、ディスクエラーが発生して処理が中断（アボート）された際に、そのドライブは自動的にアンロックされます。

ロックおよびアンロック操作を行うと、そのドライブのすべてのバッファがフラッシュ（書き出し）され、無効化されます。また、メディア用にキャッシュされていたディスクパラメータも削除されるため、次回のアクセス時にメディアから再読み出しが行われます。

デバイスベースのドライバーに関連付けられた「着脱不可能（固定）」なデバイスに対してもロック処理を適用できますが、Nextorはもともとそうしたデバイスに対してメディアチェンジ状態の確認を行わないため、ロックを行う実質的な意味はありません。

ロック機能の使用には注意が必要です。ドライブをアンロックせずにデバイスを取り外して交換すると、元のメディアと新しく挿入されたメディアの両方でデータ破損が発生する恐れがあります。

### 3.8. デバイスドライバー情報の取得 (_GDRVR, 78h)

```
パラメータ:  C = 78H (_GDRVR)
             A = ドライバーインデックス、またはスロットとセグメントを直接指定する場合は0
             D = ドライバーのスロット番号（A=0の場合のみ）
             E = ドライバーのセグメント番号（ROM内ドライバーの場合はFFh、A=0の場合のみ）
             HL = 64バイトのデータバッファへのポインタ

結果:        A = エラーコード
             HL = ドライバー情報が書き込まれたバッファ
```

システム内に存在するデバイスドライバーの情報を返します。この関数はMSX-DOS 1モードでも動作します。

デバイスドライバーは、インデックス、またはスロットとセグメント番号のペアで指定できます。インデックスで指定する場合は、Aレジスタにインデックス番号（1から開始）を設定します。呼び出しが成功すると、そのドライバーのスロットおよびセグメント番号が、他のドライバー情報とともにデータバッファに返されます。これは、システム内にどのようなドライバーが存在するかを探索する際に便利です。

情報を取得したいドライバーのスロットおよびセグメント番号がすでに判明している場合は、それらをDおよびEレジスタに設定し、A=0 として呼び出します。この場合も、バッファには同様にスロットとセグメント番号が格納されて返されます。

指定されたインデックスに対応するドライバーが存在しない場合、または指定されたスロットとセグメントのペアにドライバーが存在しない場合は、`.IDRVR` エラーが返されます。システム内にいくつのドライバーが存在するかを事前に知る方法はないため、すべてのドライバーを探索するには、インデックス1から始めて `.IDRVR` エラーが発生するまでインデックスを増やしながら、この関数を繰り返し呼び出す必要があります。

データバッファに返される情報の構成は以下の通りです。

```
+0: ドライバーのスロット番号
+1: ドライバーのセグメント番号（NextorまたはMSX-DOSカーネルROM内に組み込まれている場合はFFh。現在のバージョンでは常にFFhです）
+2: ブート時にこのドライバーに割り当てられたドライブ文字の数
+3: ブート時にこのドライバーに割り当てられた最初のドライブ文字（A:=0等。ブート時にドライブが割り当てられなかった場合は未使用）
+4: ドライバーフラグ:
    bit 7: 1 => Nextorドライバー
           0 => MSX-DOSドライバー（MSX-DOSカーネルROMに組み込まれているもの）
    bits 6-3: 未使用（常に0）
    bit 2: DRV_CONFIGルーチンを実装している場合は1
    bit 1: 未使用（常に0）
    bit 0: 1 => デバイスベースのドライバー
           0 => ドライブベースのドライバー
+5: ドライバーのメジャーバージョン番号
+6: ドライバーのセカンダリバージョン番号
+7: ドライバーのリビジョン番号
+8: ドライバー名（左詰め、スペース埋め、32バイト）
+40..+63: 予約領域（現在は常に0）
```

MSX-DOSドライバーの場合、ドライバーフラグバイトは常に0になり、ドライバーのバージョン番号やドライバー名の情報は返されません。

※Nextorはバージョン2.0.5以降から `DRV_CONFIG` ルーチンを使用するようになりました。詳細は『Nextor 2.1 Driver Development Guide』を参照してください。

### 3.9. ドライブ文字情報の取得 (_GDLI, 79h)

```
パラメータ:  C = 79H (_GDLI)
             A = 物理ドライブ (0=A:, 1=B: 等)
             HL = 64バイトのデータバッファへのポインタ

結果:        A  = エラーコード
             HL = ドライブ情報が書き込まれたバッファ
```

指定されたドライブ文字に関する情報を返します。この関数はMSX-DOS 1モードでも動作します。

データバッファに返される情報の構成は以下の通りです。

```
+0: ドライブステータス
    0: 未割り当て
    1: NextorまたはMSX-DOSドライバーに接続されたストレージデバイスに割り当て済み
    2: 未使用
    3: ドライブにファイルがマウントされている
    4: RAMディスクに割り当て済み（他のすべてのフィールドは0になります）
+1: ドライバーのスロット番号
+2: ドライバーのセグメント番号（NextorまたはMSX-DOSカーネルROM内に組み込まれている場合はFFh。現在のバージョンでは常にFFhです）
+3: ドライバー内における相対ドライブ番号（ドライブベースのドライバーのみ有効。デバイスベースのドライバーの場合はFFh）
+4: デバイスインデックス（デバイスベースのドライバーのみ有効。ドライブベースおよびMSX-DOSドライバーの場合は0）
+5: 論理ユニット（LUN）インデックス（デバイスベースのドライバーのみ有効。ドライブベースおよびMSX-DOSドライバーの場合は0）
+6..+9: デバイスの開始セクター番号（デバイスベースのドライバーに属するデバイスのみ有効。ドライブベースおよびMSX-DOSドライバーの場合は常に0）
+10..+63: 予約領域（現在は常に0）
```

ドライブにファイルがマウントされている場合、バッファに返される情報は代わりに以下のようになります。

```
+1: マウントされたファイルが存在するホストドライブ (0 = A: 等)
+2: フラグ:
    bit 0: マウントモード（0 = 読み書き可能、1 = 読み取り専用）
+3: 常に 0
+4: 印字可能形式のファイル名（最大12文字、末尾にゼロ終端を含む）
+17: ファイルの開始クラスター番号（2バイト、利用できない場合は0）
+19: ファイルの開始セクター番号（4バイト、利用できない場合は0）
```

システムがサポートする最大ドライブ番号を超えるドライブを指定した場合、`.IDRV` エラーが返されます。Nextorにおいて有効なドライブ番号であるものの、現在どのドライバーにも割り当てられていないドライブを指定した場合は、エラーは返されず、空の情報ブロックが返されます（ドライブステータスバイトをチェックしてください）。

「デバイスの開始セクター番号」は、ドライブの論理セクター0として扱われる、デバイス上の絶対セクター番号です。通常、これはデバイスのパーティションの開始セクター、またはパーティションが存在しないデバイスの場合は絶対セクター0を指します。ドライブがデバイスベースのドライバー上のブロックデバイスに割り当てられているかどうかを判別するために、この値が0であるか否かを直接テストすることは避けてください（この用途には「ドライブステータス」フィールドを使用してください）。

マウントされたファイルに対する「開始クラスター」および「開始セクター」フィールドは、Nextor 2.1.1から導入されました。現行バージョンでは常に意味のある値が返されますが、将来のバージョンで「クラスター」の概念を持たない非FATファイルシステムがサポートされた場合などには、これらのフィールドに0が格納される可能性があります。また、2.1.1より前の古いNextorバージョンでもこれらのフィールドは0として返されるため、これらの情報を使用するアプリケーションは、値が非ゼロであることを確認してから利用するように設計してください。


### 3.10. デバイスパーティション情報の取得 (_GPART, 7Ah)

```
パラメータ:  C = 7AH (_GPART)
             A = ドライバーのスロット番号
             B = ドライバーのセグメント番号（ROM内ドライバーの場合はFFh。現行バージョンでは常にFFhを指定）
             D = デバイスインデックス
             E = 論理ユニット（LUN）インデックス
             H = プライマリパーティション番号（1〜4）
             H:7 = 0: パーティションに関する情報を取得
                   1: パーティションテーブルのエントリを保持するデバイスセクター番号を取得
             L = 拡張パーティション番号（プライマリパーティションテーブルのエントリを指定する場合は0）

結果:        A = エラーコード
             【パーティション情報を要求した場合】:
                 B = パーティションタイプコード
                 C = パーティションのステータスバイト
                 HL:DE = パーティションの開始絶対セクター番号
                 IX:IY = パーティションのセクター数（サイズ）
             【パーティションテーブルのエントリが存在するセクター番号を要求した場合】:
                 HL:DE = パーティションテーブルエントリを保持するデバイスセクター番号
```

デバイスパーティションに関する情報を返します。この関数はMSX-DOS 1モードでも動作します。

この関数はデバイスベースのドライバーに対してのみ機能します。存在しないドライバー、ドライブベースのドライバー、あるいはMSX-DOSドライバーが A および B で指定された場合は、`.IDRVR` エラーが返されます。指定されたデバイス、または論理ユニットがドライバー内に存在しない場合は、`.IDEVL` エラーが返されます。

通常、ストレージデバイスは「パーティション」と呼ばれる、メディア上の連続したセクターブロックに分かれた独立した論理ボリュームに分割されています。この関数を使用すると、メディア内における任意のパーティションの開始セクターを見つけることができます。一般的には、得られたセクター情報をもとに `MAPDRV` 関数を呼び出してドライブ文字にマッピングし、Nextorからファイルシステムにアクセスできるようにするために使用されます。

パーティションタイプコードは、そのパーティションが保持しているファイルシステムの種類を示します。コードの値には以下のようなものがあります。

```
0: なし（指定された番号のパーティションが存在しない）
1: FAT12
4: FAT16（32MB未満、旧仕様）
5: 拡張パーティション (CHS)（下記参照）
6: FAT16 (CHS)
14: FAT16 (LBA)
15: 拡張パーティション (LBA)
```

**注意:** Nextor 2.1.2より前のバージョンでは、タイプコード5（拡張CHS）のみを拡張パーティションとして認識し、FDISKも拡張パーティション作成時にこのコードを使用していました。Nextor 2.1.2以降では、FDISKは拡張パーティション作成時にタイプコード15（拡張LBA）を使用するようになり、`_GPART` による既存パーティションのスキャン時においても、5と15の両方が有効な拡張パーティションタイプコードとして認識されます。以下の説明における「拡張パーティション」は、「拡張CHSまたは拡張LBAのいずれか」を指します。

他にも多数のパーティションタイプコードが存在しますが、それらはNextorが扱えないファイルシステムを指しているため、ここでは省略しています。

デバイスは、1から4まで番号付けされた最大4つのプライマリパーティションを持つことができます。4つを超えるパーティションを収容するために、パーティション番号2は「拡張パーティション」と呼ばれる特殊なタイプに割り当てられることがあります。拡張パーティションは、内部にさらに複数のパーティションを包含するためのコンテナ（容器）として機能し、そこに含まれる追加のパーティション数に制限はありません。なお、パーティション2が拡張パーティションである場合、プライマリパーティション3および4は存在しません。

デバイス内に存在するすべてのパーティションを網羅的に列挙するには、拡張パーティションの存在を考慮して、以下の手順を実行する必要があります。

1. パーティション 1-0（プライマリ番号1、拡張番号0）を探索します。

2. パーティション 2-0 を探索します。これが存在し、かつタイプが「拡張パーティション」である場合は、パーティションコード 0 が返されるまで、パーティション 2-1、2-2、2-3... と順に探索を続けます。

3. パーティション 2-0 が存在しない、または拡張パーティションタイプではない場合は、パーティション 3-0 および 4-0 を探索します。

デバイスにパーティションが一切存在しない場合もあります。この場合でも、絶対セクター0から有効なファイルシステムが開始されていれば、直接アクセスが可能です。これは、フロッピーディスクや、きわめて容量の小さいデバイスにおける一般的な構成です。

パーティションがドライブ文字にマッピングされる際、Nextorは常にそのパーティションの最初のセクター（ブートセクター）を読み込んで実際のファイルシステムタイプを判別します。パーティションタイプコードのみを鵜呑みにしてファイルシステムの種類を決定することはありません。

Nextorはパーティションを検索するためにデバイスを読み取る必要があります。デバイスへのアクセス時にエラー（例: ドライブノットレディ等）が発生した場合は、そのエラーコードが返されます。この際、システム標準のエラーハンドラや、`_DEFER` で定義されたユーザーエラーハンドラは**呼び出されません**。

指定されたパーティションがデバイスに存在しない場合（例: 4を超えるプライマリパーティション番号を指定した、または拡張パーティションを持たないプライマリパーティションに対して拡張パーティション番号を指定したなど）、`A = .IPART` が返されます。

Nextor 2.1.0 beta 2以降では、パーティション情報そのものを取得する代わりに、そのパーティションテーブルを保持しているデバイスセクター番号を要求できるようになりました。これは、パーティションテーブルのエントリを編集するアプリケーションを開発する際に役立ちます。返されたセクター内でのパーティションテーブルエントリの特定方法は以下の通りです。

* プライマリパーティションを要求した場合（拡張番号が0の場合）、返されるセクター番号は常に0となり、セクター内におけるパーティションテーブルエントリのオフセットは、プライマリパーティション1、2、3、4に対してそれぞれ 1BEh、1CEh、1DEh、1EEh となります。

* 拡張パーティションを要求した場合（プライマリパーティション番号が2で、拡張パーティション番号が0以外の場合）、パーティションテーブルエントリは返されたセクターの先頭位置（オフセット 1BEh）に配置されています。

パーティションテーブルの構造に関する詳細な情報は、Wikipediaの「マスターブートレコード」などの項目を参照してください。


### 3.11. Call a routine in a device driver (_CDRVR, 7Bh)

```
パラメータ:  C = 7BH (_CDRVR)
             A = ドライバーのスロット番号
             B = ドライバーのセグメント番号（ROM内ドライバーの場合はFFh。現行バージョンでは常にFFhを指定）
             DE = ルーチンのアドレス
             HL = ルーチンへの入力レジスタ値を保持する8バイトのバッファアドレス

結果:        A = エラーコード
             BC, DE, HL = ルーチンからの実行結果
             IX = ルーチンが返したAFレジスタの値
```

デバイスドライバー内のルーチンを直接実行します。この関数はMSX-DOS 1モードでも動作します。

MSX-DOSドライバー、デバイスベースドライバー、ドライブベースドライバーのいずれのタイプでも本関数を介して呼び出すことができますが、主な用途としては、デバイスベースのドライバーにおいてデバイス情報を列挙（`DEV_INFO` および `LUN_INFO`）したり、デバイスの絶対セクターに直接アクセス（`DEV_RW` ルーチン）して、デバイスのパーティショニングツールなどを実装するために使用されます。デバイスドライバーで利用可能なルーチンの仕様については、別紙『Nextor 2.1 Driver Development Guide』で詳しく説明されています。

ルーチン実行時のレジスタ AF、BC、DE、HL の初期値は、HLが指す8バイトのバッファにあらかじめ設定しておく必要があります。バッファ内における各レジスタ値の格納順序は、F, A, C, B, E, D, L, H です。一方、実行後のレジスタの出力値は各レジスタ（BC、DE、HL）に直接返されます。ただし、AFレジスタの出力値だけは IX レジスタに格納されて返されます。

いくつかのルーチンは、ユーザーが指定したメモリバッファとの間でデータの読み書きを行います。このようなバッファを介してドライバーのルーチンとデータをやり取りする際には、2つの制約があります。まず、バッファはプライマリマッパーのスロットに存在している必要があります。次に、バッファの一部または全体がページ1に重なっていてはなりません。これらの制約は、レジスタ初期値を設定する8バイトの入力バッファには適用されません（ただし、Nextorの関数呼び出しを `F37Dh` フック経由で呼び出す場合は、ページ1にパラメータバッファを配置できない制約が適用される点に注意してください）。レジスタ設定用の8バイトバッファは、ドライバーのルーチンが実際に実行される前にのみ使用されるため、データ転送用のバッファと領域が重複していても問題ありません。

指定されたドライバーがシステムに存在しない場合、`.IDRVR` エラーが返されます。あらかじめ `_GDRVR` 関数を使用して、存在するドライバーの位置を特定しておいてください。

### 3.12. ドライブ文字とドライバー/デバイスのマッピング (_MAPDRV, 7Ch)

```
パラメータ:  C = 7CH (_MAPDRV)
             A = 物理ドライブ (0=A:, 1=B: 等)
             B = 実行するアクション
                 0: ドライブのマッピングを解除
                 1: ドライブをデフォルト状態にマッピング
                 2: 指定されたマッピングデータを使用してマッピング
                 3: ドライブにファイルをマウント
             HL = マッピングデータを保持する8バイトバッファのアドレス（B=2の場合）
                  マウントするファイル名、またはFIBのアドレス（B=3の場合）
             D = ファイルのマウント形式（B=3の場合）
                 0: 自動（ファイル属性に読み取り専用があれば読み取り専用、それ以外は読み書き可能）
                 1: 読み取り専用
結果:        A = エラーコード
```

指定したドライブ文字に対して、デバイスベースドライバー内の特定の「デバイス番号」「論理ユニット番号」「開始絶対セクター番号」の組み合わせを割り当てます（マッピングします）。また、マッピングをデフォルト状態（起動時の状態）に戻したり、ドライブを完全に未割り当て（マッピング解除）状態にすることも可能です。この関数は、一部の制限（下記参照）付きでMSX-DOS 1モードでも動作します。

B=0 を指定して呼び出すと、指定したドライブのマッピングが解除されます。これ以降、該当ドライブは使用不能となり、アクセスしようとすると「Invalid drive」エラーが発生します。すでにマッピングが解除されているドライブに対して実行した場合は、何も起こらず、エラーも返されません。

B=1 を指定して呼び出すと、ドライブはデフォルト状態に戻ります。起動時に該当ドライブが未割り当てであった場合、またはMSX-DOSドライバーやドライブベースのドライバーにマッピングされていた場合は、それと同じ状態に戻されます。起動時にデバイスベースのドライバーに割り当てられていた場合は、そのドライブに対して自動割り当て（自動マッピング）処理が再実行されます。この自動割り当てのルールは、起動時に実行されるもの（『Nextor 2.1 ユーザーマニュアル』に記載）と同じですが、パーティションの「アクティブ」フラグのチェックはスキップされます。この結果、取り外し可能なメディアの存在状況や他のドライブの割り当て状態に応じて、起動時と同じマッピングに復元されるか、異なるマッピングになるかが決まります。

B=1によるマッピング処理において、適切なデバイスやパーティションが見つからずに失敗した場合、該当ドライブは前回の状態に関わらず「マッピング解除」状態となり、`.IDEVL` エラーが返されます。

B=2 を指定して呼び出すと、HLで指定されたバッファ内のマッピングデータに従ってドライブがマッピングされます。この方法を使用すれば、システム上の任意のドライブ文字を、任意のデバイスベースのドライバーにマッピングできます。起動時に未割り当てであったドライブや、異なるドライバーに割り当てられていたドライブであってもマッピング可能です。マッピングデータバッファの内容は以下のように構成します。

```
+0: ドライバーのスロット番号
+1: ドライバーのセグメント番号（ROM内ドライバーの場合はFFh。現行バージョンでは常にFFhを指定）
+2: デバイス番号
+3: 論理ユニット（LUN）番号
+4..+7: 開始絶対セクター番号
```

指定されたドライバーが存在しない、またはデバイスベースのドライバーではない場合は `.IDRVR` エラーが返されます。また、指定されたドライバー内に該当するデバイス番号や論理ユニットが存在しない場合は `.IDEVL` エラーが返されます。これらのエラーが発生した場合は、元のドライブマッピングは変更されずに維持されます。

指定したドライブが `H:` であり、かつRAMディスクが存在している場合は、`.RAMDX` エラーが返されます。

「開始絶対セクター番号」は、そのドライブにおける論理セクター0として扱われるセクターの番号です。通常は、`_GPART` 関数で取得したパーティションの開始セクターを設定します。ただし、この関数自体の実行時には、指定されたセクターにNextorが認識可能な有効なファイルシステムが存在するかどうかの検査は行われません。したがって、有効なファイルシステムが存在しないセクターをマッピングした場合でも関数呼び出し自体は成功しますが、その後に該当ドライブへアクセスした時点で「Not a DOS disk」エラーが発生します。

メディアが挿入されていない着脱式デバイスに対してもマッピングを実行できます。この場合も関数自体は成功しますが、その後のアクセス時に「Disk offline」エラーが発生します。

同じドライバー、デバイス、論理ユニット、および開始セクターの組み合わせを、複数の異なるドライブ文字に重複してマッピングすることはできません。これは、キャッシュバッファの不整合によるデータの破損を防ぐための仕様です。重複マッピングを試みた場合は `.IDEVL` エラーが返されます。ドライブ文字を変更したい場合は、先に古いドライブ文字のマッピングを解除しておく必要があります。

また、MSX-DOSドライバーやドライブベースのドライバーに対して、手動で明示的にマッピングを実行することはできません。

ドライブのマッピングを変更する前に、本関数は該当ドライブに関連して開かれているすべてのファイルハンドルを強制的にクローズします。これは各ファイルハンドルに対して `CLOSE` 関数を実行するのと同等であるため、もし未書き込みのバッファが存在し、かつデバイスへの書き出し（フラッシュ）でエラーが発生した場合は、ディスクエラーが返されることがあります。

MSX-DOS 1モードで本関数を実行する場合、以下の制限が適用されます。

* 対象ドライブは、起動時にデバイスベースのドライバーにマッピングされていたものである必要があります。起動時に未割り当てだったドライブや、MSX-DOSドライバー、Nextorのドライブベースドライバーにマッピングされていたドライブの割り当てを変更することはできません。

* 新しいマッピング先として異なるパーティションやデバイスを指定することは可能ですが、ドライバーのスロット番号は起動時に割り当てられていたものと同じである必要があります（システム内にNextorカーネルが1つしかない通常構成であれば、これは問題になりません）。
これらの制限は、Nextorのアーキテクチャ上の制約によるものです。

B=3 を指定して呼び出すと、HLで渡されたファイル名またはFIBが示すファイルがドライブに「マウント」されます。ファイルマウント機能はNextor 2.1.0から利用可能で、Nextor 2.1.1以降では、マウント対象のファイルがホストファイルシステム上で連続したセクターに保存されている必要があります。ファイルサイズが小さすぎる（512バイト未満）か、または大きすぎる（32MB超）場合は `.BFSZ` エラーが返されます。ファイルが連続したセクターに配置されていない場合は `.ICLUS` エラーが返されます。


### 3.13. ドライバーのZ80アクセスモードの有効化/無効化 (_Z80MODE, 7Dh)

```
パラメータ:  C = 7DH (_Z80MODE)
             A = ドライバーのスロット番号
             B =  00H => 現在のZ80アクセスモードを取得
                  01H => Z80アクセスモードを設定
             D =  00H => Z80アクセスモードを無効化（B=01Hの場合のみ）
                  FFH => Z80アクセスモードを有効化（B=01Hの場合のみ）

結果:        A = エラーコード
             D = 指定されたドライバーの現在のZ80アクセスモード（入力時と同様）
```

※この関数は MSX turboR コンピュータ上でのみ動作します。MSX1/2/2+環境では常に `.IDRVR` エラーを返します。

MSX-DOSドライバー（MSX-DOSカーネルROMに組み込まれているドライバー）に対する「Z80アクセスモード」の有効/無効を設定します。このモードが有効になっている場合、Nextorは関連するドライブにアクセスする直前に、CPUをZ80モードに切り替えます。無効になっている場合はCPUの切り替えを行わないため、R800高速モードを維持したまま、そのドライバーに接続されたドライブにアクセスすることが可能です。

コンピュータの起動直後は、すべてのMSX-DOSドライバーにおいてZ80アクセスモードが有効になっています。これは、一部の古いデバイスドライバーがR800モードでのアクセスに対応しておらず、起動できなくなるのを防ぐための仕様です。システムの起動処理が完了した後は、本関数を使用して、任意のMSX-DOSドライバーに対して個別にZ80アクセスモードを無効（または必要に応じて再有効化）にすることができます。

なお、Z80アクセスモードの設定はドライバー単位で適用され、そのドライバーに属するすべてのドライブに影響します。同一ドライバー内の特定のドライブだけを個別に有効・無効にすることはできません。

Z80アクセスモードが適用されるのはMSX-DOSドライバーのみです。Nextor独自のドライブベースおよびデバイスベースのドライバーにアクセスする際、Nextorが自動的にCPUを切り替えることはありません。


### 3.14. FATドライブ上のクラスター情報の取得 (_GETCLUS, 7Eh)

```
パラメータ:  C = 7EH (_GETCLUS)
             A = ドライブ番号 (0=デフォルト, 1=A: 等)
             DE = クラスター番号
             HL = 16バイトのバッファへのポインタ
結果:        A = エラーコード
```

指定されたドライブがFAT12またはFAT16ファイルシステムとしてマッピングされている場合、その特定のクラスター番号に関連する各種情報をユーザーが指定したバッファに書き込みます。この関数を `RDDRV` や `WRDRV` と組み合わせることで、デフラグツールなどの低レベルのディスク操作を行うユーティリティを実装することができます。

バッファに返される情報は以下の通りです。

* +0: 対象クラスターのエントリが含まれているFATセクター番号（2バイト）
* +2: FATセクター内における、対象クラスターのエントリのオフセット (0-511)（2バイト）
* +4: 対象クラスターが参照している、データ領域の最初のセクター番号（4バイト）
* +8: 対象クラスターのFATエントリの値（2バイト）
* +10: 対象ドライブにおける1クラスターあたりのセクター数（1バイト）
* +11: フラグ（1バイト）
  * bit 0: ドライブがFAT12ファイルシステムの場合にセット
  * bit 1: ドライブがFAT16ファイルシステムの場合にセット
  * bit 2: クラスターのFATエントリが奇数番目のエントリ（Odd entry）である場合にセット（FAT12のみ有効）
  * bit 3: クラスターがファイルの終端（Last cluster）である場合にセット
  * bit 4: クラスターが空き状態（Free）である場合にセット
  * bits 5-7: 未使用（常に0）
* +12-+15: 未使用（常に0）

対象ドライブがFAT12でもFAT16でもない場合、この関数は `.NDOS` エラーを返します。したがって、関数が正常に終了した場合は、常にFAT12フラグまたはFAT16フラグのいずれかがセットされていることになります。ただし、将来のバージョンで他のFATバリアントがサポートされた場合にはこの前提が崩れる可能性があるため、一方のフラグがクリアされているからといって、もう一方が必ずセットされているとは仮定せず、両方のフラグを適切にチェックするようにプログラムを記述してください。

指定されたクラスター番号がドライブの有効範囲外である場合は、`.ICLUS` エラーが返されます。なお、0および1は常に無効なクラスター番号です（最初のFATセクターにあるこれらのエントリ領域はシステム用として予約されているためです）。

FATエントリに格納されている値は、標準的なFATファイルシステムにおける一般的な意味を持ちます。

* 0: そのクラスターは空き状態です。
* FAT12では 0FF8h〜0FFFh、FAT16では FFF8h〜FFFFh: ファイルの終端（最後のクラスター）であることを示します。
* それ以外の値: ファイルのデータが継続する、次のクラスター番号を示します。

プログラムの利便性のために、値そのものを自前で判定しなくても、バッファ内のフラグ（クラスターが空き状態、終端クラスターなど）をチェックするだけで簡単に検知できるようになっています。

FAT12のエントリには「偶数番目（Even）」と「奇数番目（Odd）」が存在し、これは「エントリは奇数」フラグで区別できます。データの格納形式はそれぞれ異なり、エントリが存在するセクター内のオフセットを「X」、Xから読み出されるバイト値を「peek(X)」とすると、値は以下のように算出されます。

* 偶数番目のエントリ: `peek(X) + ((peek(X+1) and &HF) * 256)`
* 奇数番目のエントリ: `((peek(X) \ 16) and &HF) + (peek(X+1) * 16)`

参考として、以下にFAT12の偶数および奇数エントリの配置例を示す図（『MSX2テクニカルハンドブック』第3章より引用・調整）を掲載します。

```
                |4 bits |4 bits |
     FAT        -----------------
開始アドレス -> |   F       0   |  メディアID
                |---------------|
             +1 |   F       F   |  ダミーエントリ
                |---------------|
             +2 |   F       F   |  ダミーエントリ
                |---------------|
             +3 |   1       2   |  クラスター2のエントリ : オフセット = 3, 値 = 412h (偶数エントリ)
                |---------------|
             +4 |   3   |   4   |  クラスター3のエントリ : オフセット = 4, 値 = 563h (奇数エントリ)
                |---------------|
             +5 |   5       6   |
                |---------------|
             +6 |   7   |   8   |  クラスター4のエントリ : オフセット = 6, 値 = 978h (偶数エントリ)
                |---------------|
             +7 |       |   9   |
                        ---------
```

FAT16のエントリはシンプルで、指定されたオフセット位置から始まる2バイトにリトルエンディアン形式で直接格納されています（`peek(X) + (256 * peek(X+1))`）。

FAT12において、セクター内オフセットが511の場合、そのエントリ情報は該当FATセクターの最後の1バイトと、次のセクターの最初の1バイトにまたがって分割して格納されます。これはFAT12でのみ発生し得る仕様です。


## 4. 新規エラーコード

Nextorの新しいシステム機能を管理する際、または操作に失敗した際のエラー状態を処理するために、新しいエラーコードが定義されています。これらのエラーは、MSX-DOS 1モードで実行されている新規の関数呼び出しからでも、同様に返されます。

定義されているエラーコードと説明は以下の通りです。

* 無効なデバイスドライバー (.IDRVR, 0B6h)

デバイスドライバーを伴う操作が要求されましたが、指定されたドライバーが存在しないか、適切なタイプではありません（例: デバイスベースのドライバーが必要な処理に対して、MSX-DOSドライバーまたはドライブベースのドライバーを指定したなど）。

* 無効なデバイスまたはLUN (.IDEVL, 0B5h)

デバイスベースのドライバー上のデバイスを伴う操作が要求されましたが、指定されたデバイスが存在しないか、指定された論理ユニット（LUN）がそのデバイス内に存在しません。

* 無効なパーティション番号 (.IPART, 0B4h)

デバイス上のディスクパーティション情報の取得が要求されましたが、指定された番号のパーティションがデバイス内に存在しません。

* パーティションは既に使用されています (.PUSED, 0B3h)

ドライブを指定されたドライバー、デバイス、および開始セクター番号にマッピングしようとしましたが、同じドライバー、デバイス、論理ユニット、および開始セクターの組み合わせが、すでに他のドライブにマッピングされています。

* ファイルがマウントされています (.FMNT, 0B2h)

マウントされているファイルを開く、書き換える、あるいはその他のマウント中のファイルに対する禁止された操作が行われました。

* 不正なファイルサイズ (.BFSZ, 0B1h)

サイズが512バイト未満、または32メガバイトを超えるファイルをマウントしようとしました。

* 無効なクラスター番号またはシーケンス (.ICLUS, 0B0h)

`_GETCLUS` 関数に引き渡されたクラスター番号がドライブ内に存在しないか、あるいは `_MAPDRV` にマウント用として引き渡されたファイルが、ホストファイルシステム上で連続したセクターに保存されていません。


## 5. 拡張マッパーサポートルーチン

従来のMSX-DOS 2に存在していた標準マッパーサポートルーチン（『MSX-DOS 2 Program Interface Specification』の "5. Mapper support routines" を参照）が拡張され、他のRAMセグメントにあるデータを読み書きしたり、ルーチンを呼び出したりするための4つの新しいルーチンが追加されました。これらは既存の `RD_SEG`、`WR_SEG`、`CAL_SEG`、および `CALLS` に類似していますが、RAMセグメント番号だけでなく、「スロット番号 + RAMセグメント番号」のペアを入力として受け取ることができます。これらのルーチンは [UNAPI RAMヘルパー仕様（UNAPI RAM helper specification）](https://github.com/Konamiman/MSX-UNAPI-specification/blob/master/docs/MSX%20UNAPI%20specification%201.1.md#4-the-ram-helper) と互換性があり、拡張BIOSによる検出メカニズムもサポートされています。これにより、UNAPI RAMヘルパーの存在を前提として記述された既存のアプリケーションは、個別にヘルパー常駐ソフトをインストールしなくても、Nextor上でそのまま動作します。

マッパーサポートルーチンのジャンプテーブル内における、これら4つのルーチンの名称とオフセット（位置）は以下の通りです。

```
+30h: CALL_MAP
+33h: RD_MAP
+36h: CALL_MAPI
+39h: WR_MAP
```


### 5.1: CALL_MAP: Call a routine in a mapped RAM segment

* 入力:
  * IYh = スロット番号
  * IYl = セグメント番号
  * IX = 呼び出し先ルーチンのアドレス（ページ1のアドレスである必要があります）
  * AF, BC, DE, HL = 呼び出し先ルーチンに引き渡すパラメータ
* 出力:
  * AF, BC, DE, HL, IX, IY = 呼び出し先ルーチンから返された結果パラメータ

指定されたスロットおよびセグメントを一時的にページ1（4000h〜7FFFh）にマッピングした状態で呼び出しを行います。そのため、呼び出し先のルーチンアドレス（IX）もページ1の範囲内である必要があります。


### 5.2: RD_MAP: Read a byte from a RAM segment

* 入力:
  * A = スロット番号
  * B = セグメント番号
  * HL = 読み出し元アドレス（上位2ビットは無視されます）
* 出力:
  * A = 指定されたアドレスから読み出されたデータ
  * F, BC, DE, HL, IX, IY は保持されます


### 5.3: CALL_MAPI: Call a routine in a mapped RAM segment, with inline routine identification

* 入力:
  * AF, BC, DE, HL = 呼び出し先ルーチンに引き渡すパラメータ
* 出力:
  * AF, BC, DE, HL, IX, IY = 呼び出し先ルーチンから返された結果パラメータ

本ルーチンは、以下のようにインラインアセンブラ形式でパラメータを記述して呼び出します。

    CALL CALLSEG

    CALLSEG:
      CALL <address of CALL_MAPI>
      DB &Bmmeeeeee
      DB <segment number>
      ;ここでは RET は不要です

ここで各引数は以下の意味を持ちます。

* `mm` はマッパースロットです。これは標準マッパーサポートルーチンで提供されるマッパー変数テーブル（『MSX-DOS 2 Program Interface Specification』の "5.2 Mapper variables and routines" を参照）におけるインデックス番号（0〜3）に相当します。

* `eeeeee` は呼び出し先ルーチンの識別インデックス（0〜63）です。これは該当セグメントのアドレス 4000h から始まるジャンプテーブルの番号を表します（0 = 4000h、1 = 4003h、2 = 4006h、等）。

このようにスロット番号とセグメント番号を詰め込んで表現する特殊な仕様により、呼び出しコマンド全体をわずか5バイトに凝縮しています。これにより、BIOSルーチン `CALLF` と同様の手法で、フックなどからこのルーチンを呼び出すことが可能になっています。


### 5.4: WR_MAP: Write a byte to a RAM segment

* 入力:
  * A = スロット番号
  * B = セグメント番号
  * E = 書き込むバイトデータ
  * HL = 書き込み先アドレス（上位2ビットは無視されます）
* 出力:
  * A = 指定されたアドレスから読み出されたデータ（書き込み後の検証用）
  * F, BC, DE, HL, IX, IY は保持されます


### 5.5. UNAPI RAMヘルパー検出手順

Nextorは、既存の [UNAPI RAMヘルパー仕様](https://github.com/Konamiman/MSX-UNAPI-specification/blob/master/docs/MSX%20UNAPI%20specification%201.1.md#4-the-ram-helper) との互換性を持たせるため、以下の仕様に沿った検出手順を実装しています。参考として、UNAPI仕様による検出手順を以下に再掲します。

> RAMヘルパーが存在するかどうかを確認し、その提供ルーチンのアドレスを取得するには、DE=2222h、HL=0、および A=FFh を設定して EXTBIO (0FFCAh) を呼び出します。RAMヘルパーがインストールされていない場合、出力時に HL=0 が返されます。インストールされている場合は、以下のレジスタ値が返されます。
>
> * HL = ページ3にあるジャンプテーブルのアドレス
> * BC = ページ3にある縮小マッパーテーブルのアドレス（提供されない場合は0）
> * A = ジャンプテーブル内のエントリ数

Nextor環境においては、以下の値が返されます。

* HL には、`CALL_MAP` のアドレス（マッパーサポートルーチンのジャンプテーブルの先頭から +30h の位置）が格納されます。
* BC には常に 0 が返されます（標準マッパーサポートルーチンがすでに存在する場合、UNAPI RAMヘルパーの仕様において縮小マッパーテーブルの提供は必須ではないためです）。
* A には常に 4 が返されます（UNAPIの標準仕様では `WR_MAP` ルーチンが定義されていないため3とされていますが、本仕様は互換性を損なわない拡張です）。


### 5.6. 破壊的変更に関する通知

Nextor 2.1.0より前のバージョン（2.1.0のアルファ版やベータ版を含む）において、今回の `RD_MAP`、`WR_MAP`、`CALL_MAP`、および `CALL_MAPI` のエントリポイントが配置されているジャンプテーブルの領域には、以前は `BLK_ALLOC` および `BLK_FREE` という別のルーチンが割り当てられていました。これらの旧ルーチンは廃止されたため、これらを使用していた既存のアプリケーションは動作しなくなり、修正が必要となる破壊的変更（breaking change）となります。

これらはNextor本体からは削除されましたが、削除されたルーチンのソースコード自体はNextorのコードベースの一部（[source/kernel/bank4/bkalloc.mac](https://github.com/Konamiman/Nextor/blob/v2.1/source/kernel/bank4/bkalloc.mac)）として公開・保管されています。もし既存のアプリケーションでこれらのルーチンが必要な場合は、該当ファイルからコードをプロジェクトにコピーし、ローカルルーチンとして直接呼び出すように変更してください。

削除された旧ルーチンの仕様については、[Nextor 2.0 プログラマーズリファレンス](https://github.com/Konamiman/Nextor/blob/v2.0/docs/Nextor%202.0%20Programmers%20Reference.md#5-extended-mapper-support-routines) のドキュメントを参照してください。


## 6. その他の機能

本セクションでは、Nextorが提供するその他の各種機能について説明します。

### 6.1. STROUT関数におけるESC-Yエスケープシーケンスバグの修正

`STROUT` 関数は、終端記号 "$" で終わる文字列を画面に出力します。MSX-DOSには、画面上の任意の位置にカーソルを移動させるためのエスケープシーケンスとして `ESC (27) "Y" (89) x+32 y+32`（x, y は座標）が用意されています。

しかし、このエスケープシーケンスの x または y 座標の値が「4」であった場合、座標パラメータとして渡されるバイト値が `36`（"$" のASCIIコード）になってしまいます。MSX-DOSはこれらを制御パラメータではなく文字列の終わりを示す "$" 記号であると誤認し、出力を途中で打ち切ってしまうという有名なバグが存在していました。

Nextorではこのバグが修正されており、ESC-Yによる画面制御シーケンスを安全に使用することができます。

### 6.2. NEXTOR.SYSバージョン番号の変更

一部のMSX-DOSコマンドラインツールの中には、`MSXDOS2.SYS`（Nextor環境では `NEXTOR.SYS`）のバージョン番号を厳密にチェックし、その値がある基準（一般的には 2.20）より低い場合に実行を拒否する挙動を示すものが存在します。現在のNextorのカーネルおよび `NEXTOR.SYS` の実バージョンは 2.1 であるため、これは不都合を招く原因となります。

この問題への回避策として、Nextor 2.0 beta 2以降では、`DOSVER` 関数が返却する `NEXTOR.SYS` のバージョン番号情報がRAM上に格納されており、任意に書き換えが可能になっています。これをコマンドラインから簡単に変更できるツールとして `NSYSVER.COM` が用意されていますが、プログラムから直接書き換える場合は以下の手順を実行します。

1. MSX-DOSモード時（ページ0がTPA RAMにマッピングされている状態）に、アドレス `0001h` に格納されている16ビットの値を読み出します。
2. 読み出した値に `32h` を加算します。
3. 加算後のアドレスが指す場所に16ビットの数値が格納されています。これが、`DOSVER` 関数の呼び出し時に DE レジスタに返却される `NEXTOR.SYS` のバージョン番号の実体です。

例えば、バージョン番号を暫定的に 2.31 に変更するためのコード例は以下のようになります。

```
ld ix,(0001h)
ld bc,32h
add ix,bc
ld (ix),31h
ld (ix+1),2
```

この書き換えによるバージョン番号の変更は一時的なものです。BASICプロンプトに抜けて `CALL SYSTEM` で復帰した場合や、コンピュータ自体を再起動して `NEXTOR.SYS` が再ロードされた際には、本来のバージョン番号に戻ります。

※これらの仕様が適用されるのは、読み込まれている `NEXTOR.SYS` が 2.0 beta 2 以降である場合のみです。

## 7. Nextorの内部仕様

本セクションでは、Nextorの一部の機能が内部でどのように動作しているかを説明します。これは、既存の各種Nextor付属ツールを介さずに、同様の機能を自作アプリなどから直接利用・制御する際の手助けとなります。

## 7.1. ワンタイムブートキー

[ワンタイムブートキー機能](Nextor%202.1%20User%20Manual.md#292-one-time-boot-keys)は、起動時にメモリのアドレス `A100h` にゼロ終端の署名文字列 `NEXTOR_BOOT_KEYS` が発見された場合に機能します。この署名が検出された場合、Nextorはキーボードから実際のキー入力を読み取る代わりに、署名に続くアドレス領域のビットマップデータをキーボードの押下状態として処理します。ビットが1のキーが「押されている」とみなされます。

| アドレス | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
|:-------:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| A111h   | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
| A112h   | F | E | D | C | B | A | 9 | 8 |
| A113h   | N | M | L | K | J | I | H | G |
| A114h   | V | U | T | S | R | Q | P | O |
| A115h   |   |   |CTRL|SHFT| Z | Y | X | W |

※現行のNextorでは、この表に示されているすべてのキー（例: 6〜9など）を起動時に使用しているわけではありません。しかし、将来のバージョンでこれらのキーに割り当てが追加された場合も、このテーブルで定義されているビットマップ位置に基づいてキーの入力が判定されます。

## 7.2. ディスクエミュレーションモード

本セクションでは、[ディスクエミュレーションモード](Nextor%202.1%20User%20Manual.md#39-disk-emulation-mode)の内部構造について解説します。

### 7.2.1. ディスクエミュレーションデータファイルのフォーマット

エミュレーションセッション中にどのディスクイメージファイルを使用するかをNextorカーネルに通知する「ディスクエミュレーションデータファイル」は、ヘッダーと、それに続く各ディスクイメージファイルの情報のテーブルで構成されています。ヘッダーの構造は以下の通りです。

| オフセット | 意味 |
|:------:|---------|
|   +0   | ゼロ終端の署名文字列 `NEXTOR_EMU_DATA` |
|   +16  | ディスクイメージファイルテーブルのエントリ数 |
|   +17  | 起動時に最初にマウントするファイルのインデックス（1から開始） |
|   +18  | エミュレーションセッション中に使用するワークエリアのアドレス。自動割り当てにする場合は0（2バイト、リトルエンディアン） |
|   +20  | 予約領域。常に0（4バイト） |

ディスクイメージファイルテーブルの各エントリは、以下の 8バイトで構成されています。

| オフセット | 意味 |
|:------:|---------|
|   +0   | ファイルが存在するデバイスの番号（エミュレーションデータファイルと同じデバイスの場合は0） |
|   +1   | ファイルが存在する論理ユニット（LUN）の番号（デバイス番号が0以外の場合のみ有効） |
|   +2   | ファイルが開始される絶対デバイスセクター番号（4バイト、リトルエンディアン） |
|   +6   | ファイルのセクター数サイズ（2バイト、リトルエンディアン） |

エントリ内のデバイス番号が0の場合、Nextorはそのディスクイメージファイルが、エミュレーションデータファイル自体と同じデバイスおよび論理ユニットに配置されているものとみなします（この場合、エントリ内のLUN番号は無視されます）。付属の `EMUFILE.COM` ツールは、作成するデータファイルと同じデバイス上にすべてのディスクイメージファイルが存在する場合、すべてのテーブルエントリのデバイス番号を0に設定してファイルを構築します。

テーブルの最後のエントリ以降に存在する追加のデータ領域は、Nextorカーネルからは無視されます。`EMUFILE.COM` ツールは、この無視される領域に登録されているディスクイメージファイルのファイル名の一覧をテキストとして格納しています。これは、コマンドプロンプトなどから `TYPE /B datafile` を実行して表示確認する目的などで使用されています。

### 7.2.2. ディスクエミュレーションモードへの移行

起動時、Nextorはディスクエミュレーションデータファイルの存在を示すポインタを検索します。このポインタ情報は、「デバイス番号＋論理ユニット（LUN）番号」および「開始絶対セクター番号」の単純な組み合わせで表されます。

※本書およびユーザーマニュアルでは便宜上「エミュレーションデータファイル」という用語を使用していますが、Nextorカーネル自体は、それが実際の「ファイル」として存在しているか否かには関知しません。カーネルが必要とするのは、エミュレーションデータが格納されている先頭セクター番号のみです。通常はファイルとして領域を確保するのが便利ですが、例えばFATの直前の予約セクターなどを直接この用途に割り当てるようなツールを実装することも原理的に可能です。

Nextorは、起動時にRAMの特定の領域に以下の情報が格納されていることを確認すると、**「ワンタイムディスクエミュレーションモード」**に移行します。

| アドレス | 内容 |
|:-------:|---------|
| A000h   | ゼロ終端の署名文字列 `NEXTOR_EMU_DATA` |
| A010h   | エミュレーションデータが含まれているデバイス番号 |
| A011h   | エミュレーションデータが含まれている論理ユニット（LUN）番号 |
| A012h   | エミュレーションデータの開始絶対セクター番号（4バイト、リトルエンディアン） |

上記のRAM情報が検出されなかった場合、Nextorは、接続されているプライマリコントローラのいずれかのデバイスの「最初のパーティションテーブルエントリ」に、以下のような特殊な記述がなされていることを確認すると、**「パーシステント（永続）ディスクエミュレーションモード」**に移行します。

| セクターオフセット | パーティションエントリオフセット | 一般的なパーティションテーブルでの意味 | Nextorエミュレーションモードでの意味 |
|:-------------:|:----------------------------:|-------------------------|----------------|
| 1BEh          | +0                           | ステータスバイト         | ビット0がセット（1）の場合、ディスクエミュレーションモードを実行 |
| 1BFh          | +1                           | 開始CHS座標             | エミュレーションデータが含まれているデバイス番号 |
| 1C0h          | +2                           | 開始CHS座標             | エミュレーションデータが含まれている論理ユニット（LUN）番号 |
| 1C1h          | +3                           | 開始CHS座標             | エミュレーションデータが格納されている絶対セクター番号の最上位バイト（MSB） |
| 1C2h          | +4                           | パーティションタイプ     | 0以外の値である必要があります |
| 1C3h          | +5                           | 終了CHS座標             | 絶対セクター番号の第3バイト |
| 1C4h          | +6                           | 終了CHS座標             | 絶対セクター番号の第2バイト |
| 1C5h          | +7                           | 終了CHS座標             | 絶対セクター番号の最下位バイト（LSB） |

例えば、エミュレーションデータがデバイス1、論理ユニット2、絶対セクター `33445566h` に配置されており、その格納先のパーティションがFAT16（タイプ0Eh）であり、かつ起動フラグ（アクティブ）が設定されている場合の、パーシステントエミュレーション用のパーティションエントリ設定例は以下のようになります（16進数表現）。

    81 01 02 33 0E 44 55 66

Nextorがエミュレーションモードを有効にするための条件は、エントリのステータスバイトのビット0がセットされており、かつパーティションタイプが0以外の値（必ずしもFATである必要はありません）になっていることです。なお、ここで指定されるデバイス番号等は「エミュレーションデータ」の位置を指すものであり、マウントされる実際のディスクイメージファイルは別のデバイスにあっても構いません。

また、Nextorは起動時に該当セクターを読み込み、データが実際に署名 `NEXTOR_EMU_DATA` で開始されていることを必ず検証します。署名が確認できない場合は、エミュレーションは実行されず、通常のブートプロセスに移行します。
